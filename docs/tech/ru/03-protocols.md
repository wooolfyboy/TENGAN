# Протоколы и форматы обмена

TENGAN общается с внешним миром по трём каналам: собственная точка доступа Wi-Fi (HTTP + SSE), USB-кабель (текстовые строки по CDC-порту) и, для обновления прошивки, HTTP-загрузка файла. Раздел описывает каждый из них так, как он реализован в коде. Источники: `src/web/web.cpp`, `src/link/serout.cpp`, `src/pc/pc.cpp`, `tools/pc_monitor/pc_monitor.py`, `tools/desktop/tengan_desktop.py`, `tools/webapp/src/core/stream.js`.

```
                 Wi-Fi AP "TENGAN-XXXX"                       USB (CDC serial)
 телефон / планшет ────────────┐                  ┌──────────────── приложение для ПК (tools/desktop)
   :80  HTTP  /  /lite /full /api/*  /update      │                  или монитор ПК (tools/pc_monitor)
   :81  SSE   /stream?want=…                      │   "@W/@Q/@G" ->   "@E/@R/@g/@X" <-
   :53  DNS   * -> 192.168.4.1                    │   "PC/PV/PM/PP/PA/TLE" ->   "KEY/AUD" <-
                               ┌──────────────────┴──┐
                               │  TENGAN (web.cpp,   │
                               │  pc.cpp, serout.cpp)│
                               └─────────────────────┘
```

Одни и те же JSON-обработчики (`apiHandle()`) и одни и те же генераторы событий (`sseTick()`) обслуживают и Wi-Fi-, и USB-клиентов, поэтому странице всё равно, по какому транспорту она работает.

## 1. Точка доступа Wi-Fi и captive-портал

Всё это существует только пока на устройстве открыт раздел **Web** (`webStart()` / `webStop()` в `src/web/web.cpp`). При выходе из раздела выключаются Wi-Fi, дополнительное сканирование Bluetooth и помощники Sub-GHz / микрофона / ИК / NFC.

| Параметр | Значение |
|---|---|
| Режим | `WIFI_AP_STA` (STA-половина нужна для сканирования сетей) |
| SSID | `TENGAN-` + последние два байта MAC в hex, например `TENGAN-A1B2` |
| Пароль | 8 цифр: FNV-1a (32 бит) по 6 байтам MAC, по модулю 10^8, с ведущими нулями; для данного устройства постоянный |
| Канал / скрытая / макс. клиентов | 6 / нет / 4 (`WiFi.softAP(ssid, pass, 6, 0, 4)`) |
| IP | `192.168.4.1` (умолчание Arduino для softAP) |
| QR на экране | `WIFI:T:WPA;S:<ssid>;P:<pass>;;`, строится через `esp_qrcode` (не более 45x45 модулей) |

**Captive-портал.** `DNSServer` на порту 53 отвечает на любое имя адресом `192.168.4.1`. Обработчик `onNotFound` HTTP-сервера отвечает `302` с `Location: http://192.168.4.1/`. Телефон проверяет связь по известным адресам, получает редирект и сам предлагает открыть страницу.

**Разделение эфира.** Точка и Bluetooth делят одно радио, поэтому пока открыт Web, Bluetooth работает с меньшей скважностью (`bleLowDuty(true)`, окно скана 45 вместо 99) и включается только когда кто-то смотрит данные BLE. Сканирование Wi-Fi-сетей (для вкладки Wi-Fi) не обходит все каналы разом: это уводит радио с канала точки и клиенты отваливаются. Вместо этого раз в 1,5 с (`SCAN_STEP_MS`) слушается один канал 90 мс; каналы 1..13 по кругу, полный круг около 20 с. Результаты хранятся по BSSID (до 64, `NET_MAX`) и забываются после 60 с тишины.

## 2. HTTP-сервер (порт 80)

### Страницы

| Маршрут | Что отдаёт |
|---|---|
| `/` | Приложение планшета (лаунчер: заставка, выбор LITE / FULL). Один gzip-файл, `Content-Encoding: gzip`, `Cache-Control: no-cache` |
| `/full`, `/tablet` | Тот же gzip-файл. `/full` скачивают Android-приложение и приложение для ПК; `/tablet` - старый адрес |
| `/lite`, `/phone` | Лёгкая страница для телефона (`src/web/web_page.h`): вкладки Overview, Bluetooth, Wi-Fi, Sub-GHz, Sound, System, Update. Язык страницы следует языку устройства (`<html lang>` дописывается при отдаче) |
| любой другой путь | `302` на `http://192.168.4.1/` |

gzip лежит в `src/web/tablet_page.h`, его генерирует `tools/webapp/build.py` из `tools/webapp/src/`. В том же заголовке есть `TABLET_HTML_SHA` (SHA-256 **несжатого** HTML, то есть версия страницы) и `TABLET_GZ_LEN`. Сборка идёт с `mtime=0`, так что одинаковые исходники дают одинаковые байты.

### API (`/api/*`)

Все маршруты API - `GET`, отвечают `application/json` с `Cache-Control: no-store` и `Access-Control-Allow-Origin: *` (приложение планшета живёт на своём origin). `?tab=` - необязательная подсказка (см. ниже). Список маршрутов - массив `API_PATHS` в `src/web/web.cpp`; все маршруты проходят через `apiHandle()`.

| Маршрут | Параметры | Назначение и ответ |
|---|---|---|
| `/api/ble` | | Обзор Bluetooth: `on`, `count`, `macs`, `dev[]` (`id`, `r` RSSI, `t` тип, `v` производитель, `n` имя, `age`, `m` число адресов), `sens` (используется в `/lite`; см. `bleJson` в `src/ble/ble_core.cpp`) |
| `/api/bledev` | `id` | Подробности одного устройства из списка (`bleDevJson`) |
| `/api/wifi` | | `{"scanned":bool,"nets":[{"s":ssid,"b":bssid,"v":производитель (OUI),"r":rssi,"c":канал,"e":"open/WEP/WPA/WPA2/WPA3/WPA2-ENT"}]}` |
| `/api/sub` | `m` режим (0 спектр, 1 монитор, 2 датчики), `b` диапазон (0..3, по умолчанию 1) | Переключает CC1101 в этот режим и отдаёт состояние (`subJson`: массивы спектра `cur`/`peak`, либо у монитора `floor`, `burst`, `events`, `rssi[]`, `ev[]`) |
| `/api/sens` | `b` диапазон | Датчики 433 МГц (режим 2): `on`, `pk`, `noise`, `sensors[]`, `last` |
| `/api/snd` | | Микрофон / звук: `en`, `ok`, `lv`, `pk`, `hz`, `e`, `b[]` (полосы 0..100) |
| `/api/pagever` | | `{"sha":"<sha256 страницы>","gz":<размер gzip>}` - версия страницы, см. раздел 6 |
| `/api/settings` | | Все настройки по страницам: `{"pages":[{"id","name","items":[{"k","name","hint","type":"enum/range/bool/info","v",…}]}]}` |
| `/api/set` | `k`, `v` | Изменить одну настройку. `enum`: имя варианта или номер; `bool`: `1/true/on`; `range`: целое. Ответ `{"ok":true,"item":{…}}` или `{"ok":false,"err":"…"}`. Тема, язык, батарея и версия здесь только для чтения («менять на устройстве») |
| `/api/label` | `id`, `n` | Дать Bluetooth-устройству имя (пустое `n` снимает). Ответ `{"ok":true,"stable":bool}`; `stable:false` значит, что устройство меняет адрес и метка пропадёт при смене |
| `/api/act` | `a`, `v` | Действия: `a=screen&v=0/1` выключить/включить экран устройства (работа продолжается); `a=leds&v=0` погасить светодиоды |
| `/api/pckey` | `k` | Медиаклавиша для ноутбука: `VOLUP VOLDN PLAY MUTE NEXT PREV`. `{"ok":true}` только если программа на ПК жива (см. раздел 4) |
| `/api/loc` | `lat`, `lon` | Планшет присылает свой GPS; по нему устройство считает небо и глобус. Отклоняется при выходе за диапазон или ровно 0,0 |
| `/api/info` | | Аптайм, батарея (`soc`, `mv`, `ma`, `t`, `tte`, `ttf`, `rem`, `full`, `usb`, `chg`), температура чипа, свободные heap/PSRAM (КБ), `cli` (клиенты Wi-Fi), `nets`, `build`, `theme`, `ver`, `lang`, `rst` / `rstStep` (причина и шаг последнего сброса, `src/core/crumb.cpp`), `ssid` |
| `/api/ver` | | `{"build":…,"slot":"<метка текущего OTA-раздела>","max":<место под новый образ>}` |
| `POST /update` | multipart, поле файла | Загрузка прошивки, см. раздел 5 |

Пока раздел Web закрыт (бывает только при работе по USB), радио-маршруты (`ble`, `bledev`, `wifi`, `sub`, `sens`, `snd`) отвечают `{"ok":false,"err":"open Web on the stick"}`; настройки, info, метки, действия, `pckey`, `loc`, `pagever` и `ver` работают.

**Подсказка `?tab=`.** Страница `/lite` и запасной опрос планшета добавляют в каждый запрос `tab=ov|ble|wifi|sub|snd|sys|upd`. `noteTab()` её запоминает, а `webTick()` по ней решает, что запускать: Bluetooth на вкладках Overview и Bluetooth, сканирование сетей на Overview и Wi-Fi и т. д. Остальное молчит («работает только то, на что смотрят»). Когда подключён SSE-клиент, решает его подписка (`want=`), а не вкладка.

**Интервалы опроса `/lite`** (`web_page.h`): Overview 3 с, Bluetooth 2 с, Wi-Fi 5 с, Sub-GHz и Sound 60 мс, System 3 с, плюс `/api/info` раз в 8 с на любой вкладке. CC1101 и микрофон сами выключаются, если их не опрашивали 4 с.

## 3. Поток SSE (порт 81)

Вторая «дверь» - отдельный TCP-сервер (`NetworkServer`) на порту 81, чтобы долгоживущий поток не блокировал HTTP-сервер. Он принимает только `GET /stream…`, на всё остальное отвечает `404`.

```
GET /stream?want=ble,wifi,snd&sm=0&sb=1 HTTP/1.1

HTTP/1.1 200 OK
Content-Type: text/event-stream
Access-Control-Allow-Origin: *
retry: 1500

event: st
data: {"name":"TENGAN","up":123,...}
```

### Подписка: `want=`

Строка запроса разбирается `parseWant()` поиском подстрок: `ble`, `wifi`, `snd`, `sub`, `pc`, `wx`, `ir`, `nfc`, `sens` в `want=` (через запятую, по умолчанию `ble,wifi`), а также `sm=` (режим Sub-GHz, по умолчанию 0) и `sb=` (диапазон, по умолчанию 1). Для `ir` и `nfc` счётчик поколений запоминается при подключении, поэтому старые нажатия не повторяются. Событие `st` шлётся всегда.

Ёмкость: 2 Wi-Fi-клиента (`SSE_NET`) и 1 слот для USB-приложения (`USB_SLOT`), всего 3. Если оба Wi-Fi-слота заняты, новое подключение вытесняет слот 0. Подписка имеет реальные последствия: `wx` включает Bluetooth, микрофон и монитор 433,92 МГц; `sens` переводит CC1101 в режим разбора пакетов; `ir` и `nfc` запускают приёмники и останавливают их через 4 с после ухода последнего подписчика.

### События

| Событие | Когда | Содержимое (JSON) |
|---|---|---|
| `st` | раз в 2 с (первое сразу при подключении) | `name`, `up` с, `bat` % (-1 если неизвестно), `mv`, `usb`, `chg`, `cli`, `heap` КБ, `theme` (`denko`/`kurenai`), `ver`, `lang`, `rst`, `rstStep`, `radio` (буквы работающих радио: `b` BLE, `w` скан Wi-Fi, `s` Sub-GHz, `m` микрофон, `p` связь с ПК, `i` ИК, `n` NFC), `lp` = `[цикл ср. мс, цикл макс. мс, кадр ср. мс, кадр макс. мс, fps, % отправленных строк экрана]` |
| `sat` | один раз за соединение, сразу после первого `st` | `{"city","lat","lon","sats":[[имя, эпоха, n0, ndot2, inc, raan0, ecc, argp0, m0, a],…]}`: элементы орбит; небо и глобус планшет считает сам (Кеплер + J2) |
| `ble` | 1 с, если подписан | `{"on","n","m","d":[[id, rssi, "тип", "производитель", "имя", возраст_с, адресов, "метка"],…]}`: до 80 устройств по убыванию RSSI; массивы вместо объектов, чтобы экономить байты |
| `wifi` | после каждого нового результата скана, не по таймеру | как `/api/wifi` |
| `snd` | каждые 40 мс (до 25/с) | `{"en","ok","lv","pk","hz","e","b":"<32 байта hex>","w":"<64 отсчёта int8 hex>"}` |
| `sub` | каждые 140 мс (около 7/с), если CC1101 запущен | как `/api/sub` |
| `pc` | 1 с | нагрузка ноутбука, см. ниже |
| `wx` | 1 с | «радиопогода»: `ok`, `cond`, `clouds`, `wind`, `rain`, `storm`, `thunder`, `trend`, `ble`, `turn`, `sub`, `subPk`, `snd`, `pk`, `hist[]`, `temp`, `hum`, `tsrc` |
| `sens` | при новом пакете 433 МГц (не чаще 150 мс) или раз в 1 с | как `/api/sens` |
| `ir` | на каждую принятую ИК-посылку | `{"p":протокол,"addr","cmd","bits","brand","rep","raw":[мкс…],"t"}` |
| `nfc` | на каждое касание карты | `{"fam","hint","uid" (маскирован),"atqa","sak","ndef":[…],"present","t"}`; без считывателя `{"err":"no reader"}` |

Событие `pc` - это `{"live":0|1, …}`; пока программа на ПК молчит, приходит только `{"live":0}`. Иначе в нём `age`, `host`, `cpu`, `ghz`, `c[]` (по ядрам), `ram`, `ru`, `rt` (ГБ), `disk`, `dr`/`dw` (МБ/с), `nd`/`nu` (КБ/с), `bat`, `plug`, `up`, `top`, `vol`, `mute`, при наличии `trk` (`t`, `a`, `app`, `play`, `pos`, `dur`; `pos` устройство досчитывает между обновлениями) и `city` (башни `[имя, cpu%, МБ, активна, место]`).

### Правила доставки

- Запись никогда не блокируется. Сокет используется с `MSG_DONTWAIT`; что не влезло, остаётся в буфере клиента (`pend`) и досылается на следующем проходе.
- События с высокой частотой (`snd`, `sub`) «сбрасываемые»: если у клиента ещё есть неотправленные данные, кадр пропускается. Клиент, у которого буфер вырос больше 24000 байт, отключается.
- Nagle выключен (`setNoDelay`), иначе маленькие кадры ждут отложенного ACK.
- Устройство считает отправленные байты и показывает на экране скорость и активные потоки (`BLE`, `WIFI`, `SUB`, `SND`, `PC`, `WX`, `IR`, `NFC`, `USB`).

### Клиентская сторона (`tools/webapp/src/core/stream.js`)

Страница открывает `EventSource("http://<host>:81/stream?want=…")` и вешает по обработчику на каждое имя события; та же таблица обработчиков `H` используется и для USB. Если поток не открылся за 5 с, страница переходит на **опрос** `/api/*` каждые 125 мс по ступенчатому расписанию (звук каждый проход, BLE каждый 8-й, `/api/info` каждый 16-й, Wi-Fi каждый 40-й, Sub-GHz каждый 2-й) и через 8 с снова пробует настоящий поток. Индикатор показывает LIVE (SSE), POLL, USB, `USB · OPEN WEB ON TENGAN` или NO LINK. Хост и порт можно задать параметрами `?host=` и `?sse=` (так работает `tools/webapp/mock.py`, имитирующий устройство).

## 4. USB-канал между палкой и компьютером

Палка определяется как USB CDC-порт (`ARDUINO_USB_CDC_ON_BOOT=1`). Скорость для нативного USB не важна; на стороне компьютера порт открывается на 115200 с выключенными DTR и RTS (иначе палка может перезагрузиться при подключении). Порт ищется по VID Espressif `0x303A`, затем по описанию (`jtag`/`esp32`), затем по имени (`/dev/ttyACM*`, `/dev/cu.usbmodem*`).

По проводу идут **текстовые строки**, заканчивающиеся `\n`. На другом конце может быть одна из двух программ, говорящих на одном семействе протоколов:

- `tools/pc_monitor/pc_monitor.py` - консольная программа (монитор ноутбука), запускается через `start_pc_monitor.bat`;
- `tools/desktop/tengan_desktop.py` - приложение для компьютера (окно со страницей FULL + тот же монитор внутри + трей, всплывашки, виджет). Порт может занимать только одна из них.

Устройство разбирает входящие строки в `src/pc/pc.cpp` (`pcPoll()` читает не больше 2048 байт за проход `loop()`; буфер строки 1024 байта, более длинная строка выбрасывается как мусор). Строки на `@` уходят в `webLinkLine()` в `web.cpp` (протокол приложения); остальные относятся к протоколу монитора.

### 4.1 Протокол монитора (ноутбук <-> палка)

От компьютера к устройству:

| Строка | Частота | Смысл |
|---|---|---|
| `PC cpu=23.4 freq=3.10 c=12,40,5,… ram=61.2 ramu=9.8 ramt=16.0 dsk=71 dr=0.0 dw=0.1 nd=12 nu=3 up=86400 top=chrome host=LAPTOP ts=<unix> tz=<сек> [bat=87 plug=1]` | 1 с | Показатели как `ключ=значение` через пробел: ЦП %, ГГц, % по ядрам (до 16), ОЗУ % / занято ГБ / всего ГБ, заполнение диска %, диск МБ/с чтение/запись, сеть КБ/с вниз/вверх, аптайм с, самая прожорливая программа, имя хоста (без пробелов), батарея. `ts` > 1700000000 ставит часы устройства (`astroSetTime`) для неба и спутников |
| `PV vol=35 mute=0` | вместе с `PC` и сразу после нажатия клавиши | Громкость ноутбука |
| `PM<TAB>играет<TAB>поз<TAB>длит<TAB>прил.<TAB>название<TAB>исполнитель` | 1 с | Что играет; поля через TAB, потому что в названиях бывают пробелы. Пустое `PM` - ничего не играет. `поз`/`длит` в секундах, -1 неизвестно |
| `PP<TAB>имя,cpu*10,МБ,активна<TAB>…` | 1 с | «Город процессов»: одна запись на программу (все её процессы вместе); до 24 башен |
| `TLE<TAB>имя<TAB>строка1<TAB>строка2` | раз в 60 с на спутник | Элементы орбит (ISS, Tiangong, Hubble). Программа на ПК качает их с CelesTrak раз в 6 ч и кэширует в `tle_cache.txt` |
| `PA <громкость*10> <частота> <32 полосы hex> <64 отсчёта hex> <64 пары L,R hex> <стерео 0/1>` | около 30/с, пока запрошено | Разбор звука ноутбука: полосы, форма волны и XY (стерео) |

От устройства к компьютеру:

| Строка | Смысл |
|---|---|
| `KEY VOLUP` / `VOLDN` / `PLAY` / `MUTE` / `NEXT` / `PREV` | Пульт: программа на ПК нажимает медиаклавишу. Шлётся, когда открыта страница «Media» раздела PC (колесо = громкость, нажатие = пауза/играть) или с планшета через `/api/pckey`. Не шлётся, если данные от ПК устарели |
| `AUD ON` | В разделе Sound при источнике «авто» или «ПК» палка просит звук; повторяется каждые 1,5 с и только пока данные от ПК живые (иначе `pcSendLine()` молчит). Сторона ПК прекращает через 4 с после последнего запроса |
| `AUD OFF` | Перестать слать `PA` |

Данные ПК считаются «живыми», пока последней строке `PC` меньше 10 с (`pcLive()`; комментарий в `pc.h` говорит про 3 с, а код использует 10). Город живой 6 с. На стороне ПК под Windows звук берётся через WASAPI loopback (PyAudioWPatch), под Linux - через монитор PulseAudio/PipeWire с помощью `sounddevice`; на macOS звук колонок недоступен, и палка показывает свой микрофон. Клавиши: виртуальные клавиши Windows, AppleScript на macOS, `playerctl` / `pactl` / `amixer` на Linux.

### 4.2 Протокол приложения (строки `@`)

Это «страница по USB» для приложения на компьютере. Wi-Fi не нужен, у компьютера остаётся интернет.

От ПК к устройству:

| Строка | Смысл |
|---|---|
| `@W want=ble,wifi&sm=0&sb=1` | Подписка (та же строка, что в URL SSE). Приложение повторяет её каждые 2 с как «я здесь» |
| `@Q <id> /api/...?a=1&b=%D0%9F` | Запрос. Путь и запрос идут в тот же `apiHandle()`, что и по HTTP; `%XX` и `+` декодируются |
| `@G <id>` | Пришли страницу |

От устройства к ПК:

| Строка | Смысл |
|---|---|
| `@E <событие> <json>` | Событие потока: те же имена и JSON, что в SSE (`st`, `ble`, `snd`, …) |
| `@R <id> <json>` | Ответ на `@Q` с тем же `id` |
| `@g <id> begin <байт gzip> <sha256>` | Начало передачи страницы |
| `@g <id> <смещение> <base64>` | Кусок: 1536 исходных байт (до 2048 символов base64); шлётся, только пока выходная очередь короче 8 КБ, чтобы не задерживать поток |
| `@g <id> end` | Конец страницы |
| `@X web` | «Раздел Web закрыт, откройте его» (не чаще раза в 1,5 с) |

Поведение:

- USB-клиент занимает третий SSE-слот. `@W` создаёт или заменяет его подписку; тот же генератор событий затем пишет строки `@E` вместо SSE-кадров. Если 6 с нет ни `@W`, ни `@Q`, слот освобождается (приложение закрыто, кабель выдернут), и радио засыпают.
- `@W` после более чем 8 с тишины считается новым подключением и **открывает раздел Web** на палке (`navOpen(&webSection)`). Если пользователь закрыл Web вручную, пока приложение подключено, палка сама его не открывает, а только отвечает `@X web`.
- Радио палки (BLE, CC1101, микрофон) приложение, таким образом, включает так же, как планшет, по той же политике.
- Страница отправляется в gzip. Приложение проверяет размер, распаковывает, сверяет SHA-256 (по длине присланной hex-строки) и повторяет до 3 раз: USB CDC изредка теряет 64-байтный пакет, что проявляется как «страница пришла не целиком» или битый gzip.
- **Очередь вывода** (`src/link/serout.cpp`). Всё, что устройство пишет по USB (`@E`, `@R`, `@g`, `KEY`, `AUD`), идёт через один кольцевой буфер 64 КБ в PSRAM, чтобы строки не перемешивались. Строки кладутся целиком (`serOutBegin` / `Part` / `End`). Запись не блокирует: `serOutPump()` пишет столько, сколько позволяет `Serial.availableForWrite()`, до 8 раз за проход цикла. «Сбрасываемые» строки (кадры звука и спектра) отклоняются, если в очереди больше 12 КБ; любая строка, не влезающая в остаток места, тоже отклоняется.

### 4.3 Как это устроено в приложении для компьютера

`tools/desktop/tengan_desktop.py` поднимает локальный HTTP-сервер на `127.0.0.1:47321` (порт постоянный, чтобы `localStorage` страницы сохранялся) и объект `Link`, владеющий последовательным портом (поток-«сторож» переподключается при потере кабеля). В **режиме USB** окно открывает `http://127.0.0.1:47321/full`: страница получена по `@G`, а приложение вставляет в неё небольшой мост `window.TENGAN_DESKTOP={mode:'usb'}` и `window.TenganUSB`:

| Локальный маршрут | Соответствует |
|---|---|
| `/__link/want?q=…` | `@W` (с добавкой подписок `ble,ir,nfc,sens,wx`, если включены всплывашки или виджет) |
| `/__link/api?p=/api/…` | `@Q`, ждёт `@R` (таймаут 3 с; `{"ok":false,"err":"timeout"}`) |
| `/__link/poll` | длинный опрос (до 0,25 с): отдаёт `[["st",{…}],["ble",{…}],…]`; `["_x","web"]` / `["_x","nostick"]` - служебные сообщения |

Затем `stream.js` подменяет `window.fetch` для URL с `/api/`, и код страницы остаётся прежним. В **режиме Wi-Fi** окно просто загружает `http://192.168.4.1/full`; если кабель тоже подключён, его использует только часть монитора. Остальные локальные маршруты (`/__app/*`) принадлежат самому приложению (лаунчер, настройки, трей, тест всплывашки) и к протоколу палки не относятся. Всплывашки и мини-виджет описаны в `tools/desktop/WIDGET.md`.

## 5. Обновление прошивки по воздуху (OTA) и откат

Раздел Web -> страница `/lite` -> вкладка **Update**. Файл отправляется как `POST /update` (`multipart/form-data`, на странице поле называется `fw`; обработчик загрузки - `otaUpload()`).

Принимаются файлы (имена из релизного workflow `.github/workflows/build.yml`):

- `tengan_firmware_ota.bin` - чистый образ приложения (`firmware.bin`);
- `tengan_full_0x0.bin` - склеенный образ для прошивки по USB с адреса 0x0.

Как обработчик их различает: он буферизует первые `0x8002` байта. Если по смещению `0x8000` лежат `AA 50` (сигнатура таблицы разделов), файл склеенный, и всё до `0x10000` (загрузчик, таблица разделов) пропускается; приложение пишется оттуда. Иначе накопленное начало пишется как есть. Первый записываемый байт обязан быть `0xE9` (сигнатура образа ESP), иначе «not an ESP32 firmware file». Файлы меньше 32 КБ отклоняются («file is too small»).

Шаги:

1. `UPLOAD_FILE_START`: радио Bluetooth выключается, чтобы весь эфир достался загрузке; на экране устройства рисуется индикатор хода (`drawWebOta`).
2. `UPLOAD_FILE_WRITE`: `Update.begin(UPDATE_SIZE_UNKNOWN)` и `Update.write()` пишут в **другой** OTA-слот (плата использует таблицу разделов `default_16MB.csv` с двумя слотами приложения). На каждый кусок вызывается `crumbFeed()`: запись во flash медленная, а сторожевой таймер главного цикла (15 с) не должен сработать. Процент хода оценивается в предположении около 2,1 МБ.
3. `UPLOAD_FILE_END`: `Update.end(true)` проверяет образ и переключает загрузочный слот. При любой ошибке вызывается `Update.abort()`, и старая прошивка остаётся активной.
4. Ответ на `POST` - `{"ok":true|false,"err":"…"}`. При успехе устройство ждёт 600 мс и перезапускается; страница просит заново подключиться к Wi-Fi палки примерно через 20 с.

**Откат.** `src/main.cpp` определяет `verifyRollbackLater()` (возвращает true), поэтому свежезаписанный слот остаётся «на проверке», пока приложение его не подтвердит. В `loop()` функция `confirmFirmware()` вызывает `esp_ota_mark_app_valid_cancel_rollback()` лишь после **15 с работы**. Если новая прошивка падает, зависает или перезагружается раньше, при следующем сбросе загрузчик запускает предыдущий слот. После прошивки по USB вызов ничего не делает. `/api/ver` показывает метку текущего слота и максимальный размер образа.

## 6. Самообновление страницы планшета

Приложение планшета - одна HTML-страница, **зашитая в прошивку**, так что на палке всегда лежит свежий интерфейс. Android-приложение (`app/android/.../MainActivity.java`, оболочка Capacitor) обновляет свою копию с палки:

1. Раз в 30 с (и через 1,5 с после возврата в приложение) оно вызывает `GET http://192.168.4.1/api/pagever` (таймаут 2,5 с) и получает `{"sha":…}`.
2. Сравнивает `sha` с версией страницы, которую показывает сейчас: это либо `pagever.txt` ранее скачанной страницы, либо `public/pagever.txt`, вшитый в APK (его пишет `tools/webapp/build.py`).
3. Если они различаются, скачивает `GET /full` (таймаут 15 с), считает SHA-256 полученных байт и принимает страницу, только если он равен объявленному `sha`. (Устройство отдаёт gzip; приложение распаковывает его по сигнатуре `1F 8B`, поэтому хэш считается от обычного HTML.)
4. Сохраняет `index.html` и `pagever.txt` в закрытое хранилище приложения (`stickpage`), указывает на него `serverBasePath` Capacitor и перезагружает WebView. Интернет не нужен, достаточно Wi-Fi палки.
5. После обновления APK скачанная страница забывается, потому что APK может оказаться новее палки.

Состояние страница показывает в шапке через плагин `TenganUpdate` (`status` / `check`): `same`, `download`, `updated`, `bad hash`, `no stick`. Новый APK нужен только при изменениях самой нативной оболочки. Приложение для компьютера в режиме USB получает ту же страницу иначе: по `@G` (раздел 4.2) с той же проверкой SHA-256.

## 7. Постоянное хранение (NVS)

Настройки хранятся через Arduino `Preferences` (NVS во flash). Пространства имён, найденные в коде:

| Пространство | Ключи | Примечания |
|---|---|---|
| `radar` | `range`, `thresh`, `ledbr`, `scrbr`, `dim`, `snd`, `mic`, `click`, `th2` (тема), `langv` + `lang`, `auled`, `ausrc`, `city`, `gpsok` / `gpslat` / `gpslon`, `tz`, `bltick`, `wftick`, `wrange`, `band`, пороги тревог `alnear`, `alnew`, `altrk`, `alnewf`, `alwarm`, `alsens`, `alwarn`, `alalarm`, `alcble`, `alcrf`, `alcsnd`, `alcprb`, `alblink`, `alplate` | Все int, кроме `gpsok` (bool) и `gpslat/lon` (float). При загрузке значения ограничиваются своими диапазонами (`src/core/settings.cpp`). Изменение помечает настройки «грязными», запись происходит через 3 с после последнего изменения (автосохранение) |
| `labels` | `l` | Blob: массив `{uint8 mac[6]; char name[21]}`, до 32 записей; при переполнении вытесняется самая старая. Имя обрезается до 20 байт по границе UTF-8 |
| `sats` | `n0..n3`, `a0..a3`, `b0..b3` | Имя спутника и две строки TLE, до `SAT_MAX` = 4; пишется только когда эпоха принятой строки `TLE` изменилась |

`langv` пишется только после настоящего выбора языка (выбор при старте или Настройки); пока его нет, при запуске показывается выбор языка. Старый ключ `lang` - лишь подсказка при обновлении с ранних тестовых сборок. `/api/set` вызывает тот же сеттер, что и меню на устройстве (`setVal`), а значит, ту же проверку и автосохранение; вызов также пишется в «чёрный ящик» (`crumb("api set k=v")`).
