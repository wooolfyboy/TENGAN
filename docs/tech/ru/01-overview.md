# Обзор и архитектура

TENGEN — «радиообозреватель» только на приём для LilyGO T-Embed CC1101 (ESP32-S3). Устройство («палка»)
слушает Bluetooth, Wi-Fi (2,4 ГГц), Sub-GHz (CC1101), ИК, NFC и звук, показывает результат на собственном
экране 320x170 и одновременно передаёт те же данные на планшет (TENGEN Tablet), в браузер телефона или на
компьютер (TENGEN Desktop). Вся тяжёлая отрисовка вида «HQ» происходит на планшете или компьютере; палка
отправляет только числа.

Раздел описывает общую картину: кто с кем общается, что делает главный цикл, как устройство экономит
энергию, как разбирается сбой и как устроен код. Подробности про выводы — в [02-hardware.md](02-hardware.md).

## 1. Компоненты и потоки данных

```
                         +-----------------------------------------+
   радио / датчики       |       ПАЛКА  (ESP32-S3, прошивка)        |
 +----------------+      |                                         |
 | BLE-устройства | ---> | NimBLE-скан (ble/)                       |
 | маяки Wi-Fi    | ---> | пассивный скан, счётчики пакетов (wifi/) |
 | 315..915 МГц   | ---> | CC1101: RSSI / фронты OOK (subghz/)      |
 | ИК-пульты      | ---> | приёмник на RMT           (probe/ir)     |
 | NFC-карты      | ---> | PN532 по I2C              (probe/nfc)    |
 | звук           | ---> | PDM-микрофон + БПФ        (audio/)       |
 +----------------+      |                 |                       |
                         |   модели разделов + экраны              |
   колесо, бок. кнопка ->|   core/ (меню, UI, ввод, питание)       |--> экран 320x170, 8 LED, динамик
                         |                 |                       |
                         |        web/  (раздел Web)               |
                         +---------+-----------------+-------------+
                                   |                 |
                      Wi-Fi AP «SSID из MAC»     USB-CDC (Serial, 115200)
                      192.168.4.1                        |
                      :80  HTTP (страница, /api/*, OTA)  |  строки: «@W/@Q/@G ...» с ПК
                      :81  SSE-поток (события)           |          «@E/@R/@g ...» на ПК
                      :53  DNS (любое имя -> палка)      |          монитор ПК: «KEY ...», «PA ...»
                                   |                     |
                    +--------------+------+    +---------+----------------+
                    | планшет / телефон   |    | компьютер                |
                    | TENGEN Tablet (APK) |    | TENGEN Desktop           |
                    | или любой браузер   |    | (pywebview) + монитор ПК |
                    | страница            |    | та же страница, но по    |
                    |   = tablet_page.h   |    | USB вместо Wi-Fi         |
                    +---------------------+    +--------------------------+
```

Главное:

- **Одна страница, два транспорта.** Страница планшета (`src/web/tablet_page.h`, gzip-блоб, который
  генерируется из `tools/webapp/`) хранится в прошивке. Планшет забирает её по HTTP и открывает SSE-поток на
  порту 81 (`/stream?want=ble,wifi,snd,...`). TENGEN Desktop запрашивает ту же страницу по USB (`@G`) и
  получает те же JSON-события строками `@E <событие> <json>`. Для прошивки USB-канал — просто третий
  «SSE-клиент» (`USB_SLOT` в `src/web/web.cpp`; `SSE_NET = 2` планшета по Wi-Fi + 1 клиент по USB).
- **Палка — источник данных, клиент — рисовальщик.** Палка шлёт компактный JSON (массивы вместо объектов,
  списки с ограничением: например, до 80 Bluetooth-устройств в потоке), страница рисует.
- **Подписки.** Клиент говорит, что ему нужно (список `want=`). Радио, на которое никто не смотрит,
  выключается (см. раздел 5).
- **Всё локально.** У точки доступа нет выхода в интернет, облака нет; DNS-сервер отвечает на любое имя
  адресом палки только затем, чтобы телефоны открывали страницу сами.
- **По USB идут два протокола в одном проводе.** Старые строки монитора ПК (`PM`, `PV`, `KEY ...`,
  `AUD ON`, `PA ...`; `src/pc/pc.cpp`) и более новый канал приложения с префиксом `@` (`webLinkLine()` в
  `src/web/web.cpp`). Весь вывод на ПК проходит через одну очередь (`src/link/serout.cpp`): кольцевой буфер
  64 КБ в PSRAM, строки кладутся целиком, пишутся без блокировки кусками по мере места в порту, а
  «сбрасываемые» строки (кадры звука и спектра) отвергаются, если в очереди уже больше 12 КБ. Итог: строки
  не перемешиваются, а зависший ПК не может заморозить палку.

Сами форматы (HTTP API, SSE-события, `@`-строки, OTA) описаны в разделе о протоколах.

## 2. Запуск прошивки (`setup()`)

`src/main.cpp`, по порядку:

1. `crumbBoot()` — прочитать причину предыдущего сброса и последний записанный шаг (раздел 7).
2. `checkWakeHold()` — если плата проснулась из глубокого сна («выключено»), нужно удерживать боковую
   кнопку `PWR_ON_MS` = 1 с; иначе сразу снова спать (случайное касание в сумке).
3. Отпустить все устройства на общей шине SPI (все CS в HIGH) и включить `BOARD_PWR_EN` (GPIO 15, питание
   периферии).
4. `Serial` с увеличенными буферами (RX 2048, TX 8192), 115200, нативный USB-CDC.
5. `inputBegin`, `displayBegin`, `ledsBegin`, `settingsBegin`, `batBegin`, `bootScreen`, `bleBegin`,
   `audioBegin`, `satBegin`, `navBegin`, первый `navDraw`.
6. `crumbWatchdogStart()` — сторожевой таймер включается только теперь, чтобы медленная анимация загрузки
   его не сработала.

Две детали нужны, чтобы на экране не мелькал мусор: `initVariant()` и глобальный конструктор с приоритетом 101
(`earlyBacklightOff()`) обнуляют вывод подсветки раньше, чем Arduino-ядро инициализируется; подсветка
включается только после первой очистки экрана (`displayBegin()`).

Ещё одно правило запуска: BLE инициализируется (`bleBegin()`), но **не сканирует**; сканирование начинается
при входе в раздел Bluetooth.

Откат OTA: прошивка, установленная по Wi-Fi, стартует как «ожидающая подтверждения». `confirmFirmware()`
вызывает `esp_ota_mark_app_valid_cancel_rollback()` через 15 с работы; если новый образ завис или
перезагрузился раньше, загрузчик вернёт прежний слот. После прошивки по USB вызов ничего не меняет.

## 3. Главный цикл

`loop()` в `src/main.cpp` — один кооперативный цикл в задаче Arduino (ядро 0 по профилю платы; задачи
микрофона и динамика закреплены за ядром 1). Один проход:

| Шаг | Вызов | Что делает |
|---|---|---|
| 1 | `crumbFeed()` | сбросить сторожевой таймер |
| 2 | `inputPoll()` | шаги колеса, нажатие колеса, боковая кнопка (короткое = назад, удержание = выключение) |
| 3 | `bleSample(now)` | выборка числа Bluetooth-устройств для логики LED-событий |
| 4 | `ledsTick()`, `batTick(now)` | анимация LED; опрос батареи раз в 2 с |
| 5 | `pcPoll(now)` | прочитать строки из USB (не больше 2048 байт за проход), передать монитору ПК или `@`-каналу |
| 6 | `webLinkPump()` | отправка страницы кусками и очередь записи в USB |
| 7 | `navTick(now)` | `tick()` открытого раздела (сканы, развёртки, веб-сервер) |
| 8 | `powerIdleTick(now)`, `confirmFirmware(now)` | автозатемнение, подтверждение OTA |
| 9 | отрисовка (если прошёл интервал кадра) | `bleUpdate`, `navDraw` (или шкала удержания питания), `settingsAutosave` |
| 10 | `perfLoop`, `perfTick`, `delay(5)` | статистика времени; пауза 5 мс |

Перед каждой значимой фазой стоит `crumb("...")` (в коде около 24 вызовов), поэтому «чёрный ящик» знает,
где был цикл.

**Темп кадров.** Отрисовка отделена от опроса:

| Состояние | Интервал кадра |
|---|---|
| обычное | `REDRAW_MS` = 66 мс (около 15 к/с), `src/core/board.h` |
| экран выставил `g_fastFrame` (3D-сцены, галерея, звук) | 33 мс (около 30 к/с) |
| затемнено (простой) | `REDRAW_MS * 4` = 264 мс |

`g_fastFrame` сбрасывается после каждого кадра, поэтому экран должен просить снова при каждой отрисовке —
когда пользователь уходит с 3D-экрана, частота падает сама.

**Модель рисования.** Каждый экран рисует в полнокадровый спрайт `spr` (`TFT_eSprite`, 16 бит, 320x170,
около 108 КБ; `src/core/display.cpp`) и заканчивает вызовом `present()` (`src/core/theme.cpp`). `present()`
отправляет только изменившиеся строки: у каждой строки считается хеш (FNV по 32-битным словам, около 1 мс на
кадр), изменившиеся строки склеиваются в полосы (разрывы до 6 строк перекрываются, чтобы было меньше команд
дисплею) и уходят на экран. Полный кадр отправляется минимум раз в 2 секунды на всякий случай. Полный кадр
занимает около 22 мс по SPI, поэтому спокойные экраны (меню, настройки) почти не занимают шину, а это важно:
по той же шине работает и CC1101. `perfRows()` считает, сколько строк реально ушло (`pushPct` в потоке,
поле `lp`).

**Вспомогательное по времени.** `msSince(now, t)` (`src/core/timeutil.h`) возвращает 0 вместо примерно
4 миллиардов, когда метка времени поставлена позже `now` (строка из USB или BLE-пакет, обработанный другой
задачей). Используйте его вместо `now - t` на `uint32_t`.

**Счётчики производительности.** `src/core/perf.cpp` копит времена цикла и отрисовки (два вызова `micros()`
за проход) и каждые 2 с сворачивает их в `g_perf`: среднее и максимум времени цикла, время отрисовки, к/с и
доля отправленных строк. Значения уходят в поток.

## 4. Разделы: одна таблица, одно меню

В интерфейсе три уровня: **главное меню** (карточки) -> **подменю раздела** (экраны с живыми числами) ->
**экран**. Код меню универсален; раздел описывает себя одной структурой `Section`
(`src/core/section.h`):

| Поле | Назначение |
|---|---|
| `title`, `r, g, b`, `icon`, `subtitle` | название карточки, цвет, значок, живая подпись под карточкой («23 устройства») |
| `enter()` / `leave()` | вход в раздел из главного меню / выход в него: здесь включают и выключают радио |
| `nScreens`, `screenInfo(i, item)`, `screenNow()` | строки подменю (0 экранов = сразу экран) |
| `open(i)` / `close()` | подменю -> экран и обратно |
| `click()`, `rotate(dir)`, `back()` | нажатие колеса, шаг колеса, боковая кнопка на экране; `back()` возвращает true, если раздел обработал сам (например, закрыл карточку подробностей) |
| `tick(now)` | вызывается на каждом проходе `loop()` **только пока раздел открыт** |
| `draw(now)` | нарисовать текущий экран |

Необязательные указатели могут быть нулевыми (например, у Bluetooth нет `tick`).

`src/core/menu.cpp` хранит состояние (`s_cur` — открытый раздел или -1, `s_menuSel`, `s_sub`, `s_subSel`) и
раздаёт ввод: `navClick`, `navRotate`, `navBack`, `navTick`, `navDraw`. Порядок карточек — массив
`SECTIONS[]` (Bluetooth, Wi-Fi, Sub-GHz, Sound, IR, NFC, Web, PC, Gallery, Settings). В главном меню видно 5
карточек, лента прокручивается вслед за выбором. `navOpen(const Section*)` позволяет открыть раздел из кода
вне меню — так приложение для ПК открывает Web при подключении по USB.

**Новый раздел** = новый файл с таблицей `const Section xxxSection = {...}`, `extern` в его заголовке и одна
строка в `SECTIONS[]` в `menu.cpp`.

Правила ввода, которые стоит знать (`src/core/input.cpp`):

- Колесо декодируется в прерывании (`encIsr`) по таблице переходов; четыре допустимых перехода дают один
  щелчок, дребезг даёт недопустимые переходы, которые взаимно гасятся. Главный цикл лишь читает атомарный
  счётчик шагов.
- Нажатие колеса: блокировка повтора 250 мс. Боковая кнопка: отпускание между 30 мс и `PWR_SHOW_MS` (600 мс)
  — «назад»; удержание дольше 600 мс показывает шкалу питания; 2 с (`PWR_OFF_MS`) — выключение.
- Когда экран затемнён, первое нажатие или шаг колеса только будят его и в интерфейс не передаются.

При первом запуске (язык не сохранён) `navClick/Rotate/Draw` перенаправляются на выбор языка (`g_langAsk`).
Настройки лежат в NVS (`Preferences`, пространство `"radar"`) и сохраняются через 3 с после последнего
изменения (`settingsAutosave`) и при выключении.

## 5. Принцип: радио работает только внутри своего раздела

Радио, микрофон и CC1101 в TENGEN **выключены в главном меню**. Раздел включает нужное в `enter()` и
выключает в `leave()`. Это экономит батарею и убирает помехи: у ESP32-S3 одно радио 2,4 ГГц на Bluetooth и
Wi-Fi.

| Ресурс | Включается | Выключается |
|---|---|---|
| Bluetooth-скан | `bleEnter()` -> `bleRadioOn()` | `bleLeave()` -> `bleRadioOff()` |
| Wi-Fi скан / захват | `wifiEnter()` (сначала гасит BLE: «одна антенна на двоих»); захват пакетов только на экранах, которым он нужен (Activity, Clients) | `wifiLeave()`: `promOff()`, `wifiRadioOff()` |
| CC1101 | `subEnter()` (инициализация при первом использовании, переключатель антенны по диапазону) | `subLeave()`: остановка приёма 433 МГц, `ccSleep()` (SPWD) |
| Микрофон (PDM, I2S0) | раздел Sound открыт | раздел Sound закрыт |
| ИК-приёмник, PN532 | раздел IR / NFC открыт | раздел закрыт |
| LED-индикация событий | только внутри раздела Bluetooth (`navActive(&bleSection)`) | `ledsOff()` при выходе |

Исключение — **раздел Web**. Он поднимает точку доступа (режим Wi-Fi `AP_STA`, канал 6, до 4 станций), а
затем решает по подпискам клиентов, что запускать (`webTick()` в `src/web/web.cpp`):

- Сканы Bluetooth и Wi-Fi следуют за подписанными потоками; если клиентов нет, значение имеет только
  вкладка, открытая на экране самой палки.
- CC1101, микрофон, ИК и NFC работают, пока кто-то их запрашивает, и останавливаются через 4 с после
  последнего запроса (клиент обязан запрашивать снова; USB-приложение повторяет `@W` каждые 2 с как «я
  здесь», а 6 с тишины означают, что приложение закрыто).
- Пока открыт Web, Bluetooth сканирует с более коротким окном (`bleLowDuty(true)`, окно 45 вместо 99), чтобы
  делить эфир с точкой доступа; на время загрузки OTA Bluetooth выключается полностью.
- Скан сетей Wi-Fi при работающей AP идёт по одному каналу (90 мс на канал), чтобы точка доступа не
  пропадала у клиентов.

TENGEN никогда не передаёт: CC1101 не переводится в TX (строб `STX` не подаётся), вывод ИК-светодиода
удерживается в LOW, PN532 только читает, захват Wi-Fi пассивный, содержимое пакетов не читается. Единственное
излучение — собственная точка доступа палки, пока открыт Web.

## 6. Энергосбережение, режим простоя и выключение

- **Автозатемнение** (Настройки, по умолчанию выключено): через 30 с, 1 мин или 5 мин (`DIM_SECS` в
  `src/core/settings.h`) без ввода с колеса и кнопки `powerIdleTick()` снижает подсветку до четверти
  выбранной яркости, а интервал кадра становится в 4 раза длиннее (264 мс). Любой ввод будит экран
  (`powerTouch()`); этот первый ввод «съедается». Планшет может также выключить экран палки
  (`g_screenOff`): работа продолжается, а любой ввод на палке включает его обратно.
- **Включение только нужного** (раздел 5) — главная экономия: в главном меню ничего не работает, кроме
  самого цикла, опроса батареи и учёта числа устройств/LED.
- **Отправка только изменённых строк** (раздел 3) снижает трафик SPI на спокойных экранах.
- **Выключение** (боковая кнопка, удержание 2 с): `powerOff()` сохраняет настройки, гасит LED, проигрывает
  анимацию выключения 1,45 с, переводит дисплей в сон (`0x28`, `0x10`), ждёт отпускания кнопки, ставит
  подсветку и `BOARD_PWR_EN` в LOW, фиксирует их `gpio_hold_en` / `gpio_deep_sleep_hold_en`, включает
  пробуждение EXT0 по боковой кнопке (GPIO 6, низкий уровень) и уходит в глубокий сон. Периферия обесточена;
  будит только кнопка (а `checkWakeHold()` требует удержания 1 с).
- **Батарея** читается только на чтение (`src/core/battery.cpp`): индикатор заряда BQ27220 и зарядник
  BQ25896 по I2C каждые 2 с; палка показывает процент, состояние зарядки, время до разряда/до полной
  зарядки.

## 7. «Чёрный ящик» (crumb) и сторожевой таймер

Цель: после зависания или сбоя на устройстве «в поле» показать, **что делала прошивка**, без кабеля и
терминала (`src/core/crumb.cpp`).

- `crumb("имя")` копирует короткую метку (до 47 символов) в память `RTC_NOINIT_ATTR` вместе с контрольным
  числом (`0x7E6A0001`). ОЗУ RTC без инициализации переживает программный сброс (panic, сторожевой таймер,
  `esp_restart`), поэтому метка остаётся после перезагрузки. Вызов достаточно дешёвый, чтобы ставить его перед
  каждой фазой цикла и в рискованных операциях (`"ble sample"`, `"web http"`, `"ir frame"`, ...).
- `crumbBoot()` вызывается первым в `setup()`: если контрольное число верно, копирует последнюю метку и
  переводит `esp_reset_reason()` в текст: `power on`, `restart`, `panic`, `int watchdog`, `task watchdog`,
  `watchdog`, `brownout`, `wake`, `other`. Panic, три вида watchdog и brownout выставляют `crumbWasCrash()`.
- После сбоя причина и шаг видны в **Настройки > Версия** («сброс: panic @ web http»), в `/api/info` (`rst`,
  `rstStep`) и в SSE-событии `st`. При чистом старте показывается только версия.
- **Сторожевой таймер.** `crumbWatchdogStart()` перенастраивает сторожевой таймер задач ESP-IDF на 15 с с
  `trigger_panic = true` и добавляет в него задачу Arduino `loop()`. `crumbFeed()` (`esp_task_wdt_reset`)
  вызывается раз за проход цикла и должна вызываться внутри любой долгой операции. Цикл, зависший больше
  чем на 15 с, вызывает panic и перезагрузку; метка, записанная непосредственно перед этим, показывает место
  зависания.
- Таймер включается в конце `setup()`, поэтому долгий запуск им не охвачен.

## 8. Память

- Внутреннего ОЗУ около 320 КБ; на плате 8 МБ восьмиканальной PSRAM и 16 МБ флеш (см.
  [02-hardware.md](02-hardware.md)).
- Большие буферы идут в PSRAM через `psAlloc<T>(n)` (`src/core/psram.h`): `heap_caps_calloc` с
  `MALLOC_CAP_SPIRAM`, а если PSRAM нет (и в симуляторе на ПК) — обычная куча. Используется для: кольца
  записи в USB (64 КБ), водопада Sub-GHz, ландшафта звука, буферов галереи. Буферы выделяются при первом
  открытии экрана и остаются.
- Спрайт кадра создаёт TFT_eSPI, которая сама предпочитает PSRAM, если она есть и DMA не включён; если
  выделить не удалось, код переходит на 8-битный спрайт.
- Палка сообщает свободную кучу и PSRAM (`/api/info`, `heap`, `psram` в КБ).
- Строки двуязычные: `L("English", "Русский")` (`src/core/lang.h`) выбирает вариант во время работы по
  `g_lang`, поэтому одна прошивка работает на обоих языках.

## 9. Структура репозитория

```
VERSION                 одна версия для прошивки, страницы, установщика, приложений (например, 2.0-test6)
platformio.ini          сборка: окружение t-embed-cc1101, выводы/флаги TFT_eSPI, -O2, библиотеки
boards/T_Embed_PN532.json   профиль платы (16 МБ флеш, PSRAM qio_opi, USB CDC)
src/main.cpp            setup() и loop()
src/core/               меню, модель разделов, примитивы экрана/темы/UI, ввод, питание, батарея,
                        настройки (NVS), LED, crumb («чёрный ящик»), perf, анимация загрузки, шрифты
src/ble/                Bluetooth: ядро скана, базы типов/производителей, экран «City»
src/wifi/               Wi-Fi: скан, каналы, активность, клиенты, база OUI
src/subghz/             драйвер CC1101, спектр/водопад/монитор, OOK-декодеры и датчики 433 МГц
src/probe/              ИК-приёмник (RMT) и NFC (PN532), только чтение
src/audio/              микрофон (PDM, БПФ), динамик (звуки интерфейса), экраны Sound
src/web/                раздел Web: точка доступа, HTTP API, SSE-поток, OTA, USB-канал приложения, страница для телефона
src/link/               очередь вывода в USB (serout)
src/pc/                 раздел PC: строки монитора ПК, управление медиа, «город» процессов
src/gallery/            Gallery, небо/планетарий, спутники (SGP4), радиопогода
tools/webapp/           исходники страницы планшета (HTML/CSS/JS), build.py -> src/web/tablet_page.h, mock-сервер

docs/                   скриншоты, материалы README; docs/tech/ — эта документация (en/, ru/)
```
