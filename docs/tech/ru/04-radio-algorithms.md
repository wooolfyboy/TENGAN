# Радиоразделы: алгоритмы

Здесь описано, как радиоразделы TENGAN превращают сырые радиособытия в то, что видно на экране. Всё работает **только на приём**: Bluetooth никогда не подключается, Wi-Fi ничего не передаёт (пассивный скан, прослушивание в promiscuous-режиме), CC1101 никогда не переводится в передачу (строб `STX` не используется), ИК-светодиод (GPIO 2) удерживается в нуле, а NFC читает только то, что карта и так сообщает всем.

| Раздел | Код | Железо | Входные данные | Результат |
|---|---|---|---|---|
| Bluetooth | `src/ble/` | радио ESP32-S3, NimBLE | рекламные пакеты | физические устройства, типы, производители, датчики погоды |
| Wi-Fi | `src/wifi/` | радио ESP32-S3, только 2.4 ГГц | маячки, заголовки пакетов | сети, загрузка каналов, клиенты, поиск по сигналу |
| Sub-GHz | `src/subghz/` | CC1101 на общей шине SPI | RSSI, демодулированный OOK на GPIO 3 | спектр, всплески, датчики 433 МГц |
| IR | `src/probe/ir*` | ИК-приёмник (GPIO 1) через RMT | длительности вспышек и пауз, мкс | протокол, адрес, команда, марка |
| NFC | `src/probe/nfc*` | PN532 по I2C (0x24) | ATQA/SAK/UID, ответы на PPSE и NDEF | семейство карты, скрытый UID, записи NDEF |

Общие правила для всех разделов:

- **Одно радио за раз.** Bluetooth и Wi-Fi делят одну антенну: вход в Bluetooth вызывает `wifiRadioOff()`, вход в Wi-Fi — `bleRadioOff()` (`bleEnter` в `src/ble/ble_core.cpp`, `wifiEnter` в `src/wifi/wifi.cpp`). При выходе из раздела его радио выключается. IR, NFC и CC1101 работают, только пока открыт их раздел или планшет подписан на них (`src/web/web.cpp`).
- **Сырые данные пишет callback или прерывание, основной цикл читает снимок.** Bluetooth использует мьютекс, Wi-Fi — атомарные счётчики и кольцевой буфер, Sub-GHz и IR — кольцевой буфер / RMT.
- **На экране «спокойные» значения.** Сырой RSSI скачет на несколько дБ, поэтому большинство экранов показывает сглаженные значения или значения с гистерезисом (подробности ниже). Сортировка и фильтры используют сглаженное значение, экран — ещё более устойчивое.

## Bluetooth (`src/ble/`)

### Файлы

| Файл | Роль |
|---|---|
| `ble_core.cpp` | callback сканера, склейка адресов, фильтр дальности, порядок списка, история, JSON для веб-страницы |
| `ble_model.h` | структуры (`Dev`, `Ent`, `Sensor`) и константы |
| `devtypes.h` | разбор рекламы, определение типа устройства, отпечаток |
| `vendors.cpp`, `vendors.h` | поиск производителя (Company ID / сервисный UUID), таблица брендов |
| `btdb.h` | сгенерированная база (`tools/gen_btdb.py`): Company ID и владельцы 16-битных UUID; подключается только из `vendors.cpp` |
| `sensors.h` | разбор рекламных пакетов датчиков погоды |
| `ble_screens.cpp`, `ble_city.cpp` | экраны: Обзор, Радар, Город, Ближайшее, Устройства, Погода |

### Сканирование

`bleBegin()` инициализирует NimBLE с активным сканом (`setActiveScan(true)`), интервал 100, окно 99 (слушаем почти непрерывно), callback на каждый пакет (`setScanCallbacks(cb, true)`), `setMaxResults(0)` — NimBLE ничего не накапливает, вся обработка идёт в `ScanCB::onResult`. Скан включается только при входе в раздел (`bleRadioOn`). В веб-режиме `bleLowDuty(true)` сужает окно до 45, чтобы Wi-Fi хватало эфира.

### Разбор рекламы

`parseAdv()` проходит по записям `[длина][тип][данные]` и извлекает: 16-битные сервисные UUID (типы 0x02/0x03 и UUID в service data 0x16, до 8), имя (0x08/0x09, полное имя важнее короткого), Appearance (0x19), manufacturer data (0xFF: Company ID, первые 8 байт и полная длина).

### Тип устройства

`classify()` возвращает один из типов: phone, computer, audio, watch, TV, tracker, beacon, input, sensor, unknown. Проверки идут в строгом порядке, побеждает первая сработавшая:

1. UUID трекеров (Tile `FEED`/`FEEC`, Samsung SmartTag `FD5A`, Chipolo `FE33`);
2. Appearance по категории (`значение >> 6`);
3. ключевые слова в имени (порядок важен: трекер, аудио, часы, ТВ, ввод, датчик, компьютер, телефон — поэтому «Galaxy Buds» это аудио, а не телефон);
4. сервисные UUID (Eddystone, Fast Pair, LE Audio, HID, пульс, Environmental Sensing, BTHome, Xiaomi);
5. manufacturer data: у Apple (Company ID `0x004C`) первый байт — тип сообщения (iBeacon, AirPods proximity pairing, AirPlay, Apple Watch, HomeKit, Find My, Nearby/Handoff). Для Find My байт статуса отличает AirTag/сторонний тег, AirPods и телефоны. Также Windows (`0x0006`), Garmin, Huami, Bose, Harman.

Если пакет распознан как датчик погоды, тип принудительно «sensor». Тип адреса обновляется только известным (не unknown) результатом, поэтому один пакет без имени не стирает тип.

### Производитель

`resolveVendor()` рассматривает Company ID и владельца каждого «не общего» сервисного UUID (`btdb.h`). Каждый кандидат получает оценку уверенности:

| Оценка | Смысл |
|---|---|
| 3 | бренд из таблицы `BRANDS` (Apple, Microsoft, Samsung, Google, Xiaomi, ...), сопоставляется по первому слову названия |
| 2 | другая названная компания |
| 1 | производитель Bluetooth-чипов (`isChipMaker`: код называет кремний, а не изделие) или код без названия |

Сохраняется лучший кандидат. UUID, которыми пользуются устройства любых брендов (`FD6F` contact tracing, `FEAA` Eddystone, `FE2C` Fast Pair), игнорируются. На экране показывается бренд, иначе название компании, иначе `0xXXXX`. База генерируется, руками не правится.

### Типы адресов и склейка ротируемых MAC

Телефоны и многие аксессуары периодически меняют случайный адрес, поэтому подсчёт MAC завышает число устройств. TENGAN объединяет адреса в одно **физическое устройство** (`Ent`).

Вид адреса определяется битом типа и двумя старшими битами адреса: public; random static (`11`); resolvable private, то есть ротируемый (`01`); non-resolvable (`00`). Ротируемые и non-resolvable — кандидаты на склейку (`rnd`).

**Отпечаток** (`advSignature`): хеш FNV-1a от того, что не меняется между пакетами одного устройства: Company ID, длина manufacturer data и её первый байт (тип сообщения), отсортированные сервисные UUID, Appearance, имя. Пустая реклама даёт 0 и никогда не склеивается.

**Правило склейки.** Когда появляется новый адрес с ненулевым отпечатком, среди уже известных ищется предшественник, который:

- тоже случайный (`rnd`) и ещё не был склеен с другим;
- имеет такой же отпечаток;
- молчит от `STALE_MIN` до `STALE_MAX` = 1.5..12 с (ещё не замолчал — вероятно, другое устройство; молчит слишком долго — ушло);
- имеет ближайший по RSSI сигнал, не дальше `MERGE_DB` = 10 дБ.

Если найден, новый адрес наследует физический id (`ent`), время первого появления, счётчик пакетов, мин/макс RSSI и, если не задано, тип, производителя и имя; старый помечается `merged` и в склейке больше не участвует. Иначе выдаётся новый физический id. Ограничения: близкие устройства с одинаковым отпечатком и похожим RSSI могут быть перепутаны; устройство, молчавшее дольше 12 с, считается новым; пустую рекламу склеить нельзя. Число сырых MAC показывается рядом с числом устройств («MAC» в Обзоре, `macs` в JSON).

### Фильтр дальности и гистерезис

Настройка «Дальность» Bluetooth — порог по сглаженному RSSI (`src/core/settings.h`):

| Название | Порог, дБм |
|---|---|
| all | -127 |
| far | -90 |
| room | -80 |
| near | -70 |
| very near | -60 |

Сглаженный RSSI: `rssiS = (3·rssiS + rssi) / 4`. Адрес входит в зону при `rssiS >= порог` и выходит, только когда `rssiS < порог - 5` (`RANGE_HYST_DB`), поэтому устройство на границе не мигает. Адреса с числом пакетов меньше `MIN_PKTS` = 2 отбрасываются (одиночные случайные пакеты). Замолчавшие адреса забываются через `REMEMBER_MS` = 30 с; одновременно хранится не более `MAX_DEVS` = 600 адресов. Каждый кадр `bleUpdate()` пересобирает карту физических устройств из адресов, прошедших фильтр: пакеты = максимум, first = самое раннее, RSSI — от самого свежего адреса, `nMacs` = число адресов.

### «Спокойный» сигнал и ближайшее устройство

Для каждого физического устройства показываемый RSSI считает `steadyRssi()`: целевое значение сдвигается, только если сглаженный сигнал отличается от него на 4 дБ (`STEADY_DB`); показываемое значение плавно подтягивается к цели с постоянной времени 0.7 с. «Ближайшее» меняется, только если другое устройство сильнее на 3 дБ (`BEST_HYST_DB`). Расстояние (`estDistance`, `src/ble/ble_screens.cpp`) — логарифмическая модель с опорой -59 дБм на 1 м и показателем 2.5, ограничено 0.1..99 м. Это грубая подсказка, а не измерение.

### Порядок списка

Список устройств «липкий»: ближайшие сверху, но соседи меняются местами, только если нижний сильнее более чем на `ORDER_HYST_DB` = 8 дБ; порядок пересчитывается каждые `ORDER_EVERY` = 2 с и замораживается, пока открыты подробности, и на `ORDER_FREEZE` = 4 с после поворота колеса. Новые устройства вставляются на своё место, исчезнувшие удаляются.

### История и детектор событий для ленты

`bleSample()` раз в секунду пишет число физических устройств в кольцо из 150 отсчётов (`HIST_N`, 2.5 минуты). Базовая линия следует за числом экспоненциальным средним (коэффициент 0.15). Если число отличается от базы не меньше чем на порог «события ленты» (`g_thresh`, по умолчанию 7, 0 = выкл.), возникает событие +1 (пришла группа) или -1 (группа ушла), база прыгает к текущему числу и включается пауза 3 с. После включения радио база обучается заново, а события молчат 10 с. Свет ленты подаётся только внутри раздела Bluetooth.

### Метки

На планшете устройству можно дать имя (до 20 байт, обрезка по границе UTF-8). Метки хранятся по MAC в NVS (пространство `labels`, до 32, самая старая вытесняется). Так как ротируемый MAC меняется, API возвращает `stable=false` для таких устройств: метка живёт, пока не сменится адрес.

### Датчики погоды (`sensors.h`)

`parseSensor()` просматривает сырой пакет и пробует все форматы. Пакеты не шифруются и читаются любым:

| Формат | Где | Поля |
|---|---|---|
| PVVX (15 байт) / ATC1441 (13 байт) | service data `181A` | температура (PVVX s16 LE /100, ATC s16 BE /10), влажность, батарея |
| BTHome v2 | service data `FCD2` | объекты по id: батарея `01`, температура `02`/`45`, влажность `03`/`2E`, давление `04`, CO2 `12`; зашифрованные пакеты (бит 0 байта info) и другие версии пропускаются |
| Xiaomi MiBeacon | `FE95` | только без шифрования; объекты `1004` температура, `1006` влажность, `100A` батарея, `100D` оба |
| Qingping | `FDCD` | температура и влажность, батарея, давление, CO2 |
| SwitchBot Meter | `FD3D` | модели `T`, `i`, `w`: батарея, температура, влажность |
| Govee | manufacturer `0xEC88` | упакованное 24-битное значение: температура и влажность; принимается, только если -40 < T < 80 |
| RuuviTag формат 5 | manufacturer `0x0499` | температура, влажность, давление; маркеры «нет данных» пропускаются |

Последние значения хранятся по адресу (до `MAX_SENSORS` = 24) в течение `SENSOR_REMEMBER_MS` = 5 минут, потому что датчики передают редко. Они показываются на экране «Погода» и уходят на веб-страницу (`sens` в `/api/ble`).

### Вывод для веба

`bleJson` (`/api/ble`, до 150 устройств), `bleStreamJson` (SSE-поток для планшета, до 80 устройств массивами) и `bleDevJson` (`/api/bledev`, все адреса одного устройства с видом, мин/макс RSSI, Company ID, UUID с владельцами, первые байты manufacturer data) читают один и тот же снимок.

## Wi-Fi (`src/wifi/`)

У ESP32-S3 только радио 2.4 ГГц: сети 5 ГГц не видны. Используются каналы 1..13 (`CH_MAX`).

### Экраны и режимы радио

| Экран | Режим радио |
|---|---|
| Сети (список + подробности) | пассивный скан, все каналы |
| Каналы | пассивный скан, все каналы |
| Активность | promiscuous, перебор каналов |
| Клиенты | promiscuous, перебор каналов |
| Поиск (FIND) | пассивный скан одного канала |

Скан и promiscuous-режим взаимоисключающи: `wifiSetMode` включает `promOn()` для Активности и Клиентов (предварительно останавливая скан) и `promOff()` для остальных. Вход в FIND и выход из него отменяют идущий скан, потому что скан всех каналов и скан одного канала смешивать нельзя. В подменю раздела (до открытия экрана) идёт обычный скан всех каналов, чтобы цифры были живыми.

### Пассивный скан

`WiFi.scanNetworks(async=true, show_hidden=true, passive=true, мс_на_канал, канал)`: ничего не передаётся, радио только слушает маячки. Полный проход — 150 мс на канал (около 2 с на 13 каналов); FIND — 110 мс и только канал цели. Сканы идут цепочкой: закончился один — стартует следующий (при ошибке повтор через 500 мс или 1 с).

Для каждого результата (ключ — BSSID) хранятся: SSID (скрытая сеть — пустой), канал, режим защиты, вторичный канал (`sec`: +1 выше, -1 ниже, 0 — обычные 20 МГц), поколение (`phy_11ax` — Wi-Fi 6, `phy_11n` — Wi-Fi 4, `phy_11g`, иначе 11b), производитель (по OUI), мин/макс RSSI, сглаженный RSSI `rssiS = (rssiS + rssi) / 2`. Показываемый `rssi` приглажен: он переходит к `rssiS` только при расхождении в 3 дБ (`WIFI_STEADY_DB`). Сети, не слышные `AP_REMEMBER_MS` = 60 с, удаляются после полного прохода.

**Производитель по OUI**: первые 3 байта BSSID, бинарный поиск по сгенерированной таблице `src/wifi/ouidb.h` (`tools/gen_ouidb.py`, данные IEEE через Nmap).

**Точка доступа телефона** (`looksLikeHotspot`): в SSID есть ключевое слово (iphone, galaxy, redmi, pixel, hotspot, ...) либо производитель по OUI — Apple, Samsung, Xiaomi, Motorola или OnePlus. На экране пометка «ТЕЛ». Открытые сети помечаются «ОТКР».

### Порядок списка

Тот же принцип, что в Bluetooth: «липкий» порядок, обмен только при разнице больше 6 дБ; заморозка, пока открыты подробности, и на 4 с после поворота колеса. Настройка «Дальность» Wi-Fi скрывает сети со сглаженным уровнем ниже порога (та же таблица дБм, что в Bluetooth; выбранная сеть остаётся). История сигнала открытой сети получает один отсчёт за полный скан (60 точек).

### Каналы и рекомендация

Каждая сеть занимает полосу с центром на номере канала `ch + 2·sec` (сеть 40 МГц центрирована между двумя каналами) и с полушириной 2 (20 МГц) или 4 (40 МГц). Помеха сети *a* каналу *k* — линейная:

```
d     = |центр(a) - k|
reach = полуширина(a) + 2 + 1    // + наши 20 МГц (±2) + запас в 1 канал
I     = d >= reach ? 0 : 1 - d / reach
```

`bestChannel()` оценивает три непересекающихся канала 1, 6 и 11. Для каждого считается сумма `I · (rssiS + 100)` по всем известным сетям; побеждает наименьшая. Чем сильнее сеть, тем больший у неё вес. Результат только показывается («лучший N»); устройство ничего не меняет. Ограничение: учитываются только маячки, замеченные сканом; нагрузка трафиком в оценку не входит.

### Активность (promiscuous-режим)

`promOn()` останавливает скан, ставит фильтр на управляющие и data-кадры, регистрирует `promCb` и стартует на канале 1 (`WIFI_SECOND_CHAN_NONE`). Обработчик (выполняется в задаче Wi-Fi, в IRAM) делает только следующее:

- считает управляющие и data-кадры (атомарные счётчики);
- накапливает уровень шума, который сообщает радио (принимается значение от -120 до -20 дБм);
- по заголовкам кадров (но не по содержимому) кладёт события в кольцо на 128 ячеек: data-кадр с ToDS/FromDS даёт пару (устройство, сеть); probe request — источник устройства, ищущего Wi-Fi. Кадры короче 24 байт и групповые адреса игнорируются.

Основной цикл (`wifiHopTick`) переходит на следующий канал каждые `HOP_MS` = 200 мс (полный круг по 13 каналам — около 2.6 с). При каждом переходе счётчики пакетов канала, который только что покинули, пересчитываются в частоты в секунду (`pps`, сглаживание 0.4/0.6 старое/новое, отдельно для управляющих и data) и в шум (среднее, сглаживание 0.5/0.5). Раз в секунду суммарный pps по всем каналам пишется в историю из 120 отсчётов (2 минуты). Экран предупреждает, если шум на канале выше -86 дБм (обычно -90..-95). Так как слушается один канал за раз, цифры по остальным каналам — последние измеренные, а не одновременные.

### Клиенты

Устройства, замеченные в data-кадрах, хранятся как (MAC устройства → BSSID сети, время) до `STA_MAX` = 500 и забываются через `STA_REMEMBER_MS` = 120 с. Источники probe request хранятся отдельно как «ищут Wi-Fi». Показываются только числа; MAC не выводятся, содержимое пакетов не читается. Случайные MAC телефонов считаются отдельными устройствами. Число клиентов сети (`clientsOf`) включает только устройства, услышанные на её канале во время перебора, поэтому это оценка снизу.

### FIND

Цель — выбранная сеть (если не выбрана, самая сильная). Скан ограничен её каналом (110 мс), поэтому результат приходит несколько раз в секунду. Каждый результат добавляет точку (история 100 точек); промах добавляет -127. Экран показывает среднее по последним 5 отсчётам, переводит его в шкалу 0..100 % (`(rssi + 95) · 100 / 60`), слово (EXCELLENT выше -55, GOOD выше -67, FAIR выше -75, WEAK выше -85, иначе BAD) и тренд: разница между последними 5 и предыдущими 5 отсчётами (±3 дБ даёт «теплее» / «холоднее»). «НЕТ СИГНАЛА» появляется, если попаданий не было 4 с. Оценка расстояния использует другую опору (`10^((-45 - rssi) / 25)` м). Тики в стиле счётчика Гейгера ускоряются вместе со шкалой (`g_wifiTicks`), лента показывает уровень. Нажатие выбирает следующую сеть целью.

## Sub-GHz (`src/subghz/`)

### Драйвер CC1101 (`cc1101.cpp`)

Минимальный, только приём. CC1101 делит шину SPI с дисплеем (4 МГц, режим 0; библиотека дисплея настраивает SPI только на запись, поэтому перед каждым обменом вызывается `SET_BUS_READ_MODE`). Выводы: CS 12, MISO 10, переключатель антенны SW1 47 / SW0 48, GDO0 3 (`src/subghz/cc1101.h`, `sens_rx.cpp`).

- `ccInit`: сброс (`SRES`), проверка чипа (PARTNUM `0x00`, VERSION `0x14`, `0x04` или `0x07`); при неудаче раздел показывает «нет чипа». Затем загружается таблица регистров: ASK/OOK, без пакетов, выводы GDO в высоком импедансе, фильтр канала 58 кГц (`MDMCFG4 = 0xF5`).
- RSSI: регистр `0x34`, пересчёт `(знаковое)/2 - 74` дБм.
- Частота: `FREQ = МГц · 65536 / 26` (кварц 26 МГц); `TEST0` переключается между `0x0B` и `0x09` в зависимости от поддиапазона (как в библиотеке ELECHOUSE).
- Переключатель антенны по частоте: ниже 350 МГц — тракт 315 (SW1/SW0 = 1/0), ниже 500 МГц — тракт 433 (1/1), выше — тракт 868/915 (0/1).
- `ccMeasure(f)`: idle, установка частоты, `SRX` (с автокалибровкой), ожидание состояния RX до 2 мс, 250 мкс на установку RSSI, чтение.
- `ccSleep` (`SPWD`) при выходе из раздела.

### Диапазоны

| Диапазон | Развёртка, МГц | Частота монитора, МГц |
|---|---|---|
| 315 MHz | 313.0..317.0 | 315.00 |
| 433 MHz | 431.92..435.92 | 433.92 |
| 868 MHz | 866.3..870.3 | 868.30 |
| 915 MHz | 913.0..917.0 | 915.00 |

Нажатие колеса переключает на следующий диапазон (выбор сохраняется в настройках). По умолчанию 433 МГц.

### Спектр и водопад

Диапазон делится на `SP_N` = 96 точек (полоса 4 МГц, шаг около 42 кГц). За один проход основного цикла измеряется 12 точек (около 15 мс), так что одна развёртка занимает примерно 8 проходов. RSSI ограничивается диапазоном -120..-10 дБм. `g_spCur` хранит текущее значение, `g_spPeak` — пик, который оседает на 1 дБ за развёртку. В конце каждой развёртки в кольцо из `WF_ROWS` = 56 строк, выделенное во внешней памяти (`psAlloc`), пишется строка водопада (`дБм + 120`, 0..110). В этом режиме фильтр узкий (`0xF5`, около 58 кГц), чтобы соседние точки не размывались. Полоса всего ±2 МГц: это взгляд на один диапазон, а не широкий сканер.

### Монитор: всплески

Чип слушает частоту диапазона с более широким фильтром (`MDMCFG4 = 0x65`), потому что брелоки и датчики «гуляют» по частоте. За проход берётся максимум из 8 замеров RSSI с интервалом 300 мкс и дописывается в историю из 300 отсчётов. Обнаружение всплесков идёт относительно уровня шума — медленного среднего (`floor = 0.98·floor + 0.02·x`), который обновляется только вне всплесков:

- всплеск начинается при `rssi > floor + 12 дБ` (`BURST_ON_DB`);
- пока `rssi > floor + 7 дБ` (`BURST_OFF_DB`), всплеск продолжается и отслеживается его пик (гистерезис);
- после 150 мс ниже этого порога всплеск заканчивается и записывается (начало, длительность до 65 с, пик); хранятся последние 6 (`EV_N`).

Во время всплеска лента вспыхивает. Записываются только время и уровень, содержимое — никогда.

### Датчики: захват OOK-импульсов (`sens_rx.cpp`)

В режимах Monitor и Sensors CC1101 переводится в асинхронный последовательный режим: демодулированный OOK (1 — несущая, 0 — тишина) выводится на GDO0 (GPIO 3), АРУ настроена под OOK. Прерывание по обоим фронтам пишет в кольцо на 2048 записей длительность только что закончившегося отрезка в микросекундах, уровень — в бите 31. Переполнение кольца считается шумом, буфер сбрасывается.

Основной цикл (`sensRxTick`) собирает **посылки**: каждый элемент — импульс и следующая за ним пауза (`OokTrain`, до 1024 пар). Посылка завершается, когда пауза превышает `TRAIN_END_US` = 20 мс, либо по таймеру, если фронтов больше нет, либо когда буфер заполнен (последний случай считается шумом и не декодируется). Отрезки короче `GLITCH_US` = 40 мкс — помехи, они склеиваются с соседями (`cleanup`). Посылки меньше 8 импульсов отбрасываются. К посылке прикладывается наибольший RSSI, замеченный монитором за это время.

### Декодирование (`ook.cpp`)

Код не зависит от железа: его собирают симулятор и тесты на компьютере (`tools/ook_test`). Нарезка битов повторяет правила открытого проекта rtl_433 (форматы и контрольные суммы описаны в его документации; код собственный), поэтому записи из его набора тестов разбираются так же.

Два «нарезчика», управляемых таблицей протоколов (короткая/длинная длительность, синхро, предел паузы, пауза сброса, допуск):

- **PPM**: бит определяет длина паузы (короткая — 0, длинная — 1);
- **PWM**: бит определяет длина импульса (короткий — 1, длинный — 0), с необязательными синхроимпульсами и окнами допуска.

Биты собираются в строки (до 48 строк по 96 бит). Декодер обычно требует, чтобы одна и та же строка повторилась (`repeated(minRep, minBits)`), потому что датчики шлют сообщение несколько раз; это сильный фильтр от шума. Затем проверяются длина, контрольная сумма/CRC и диапазоны значений. На посылку выдаётся один датчик (одинаковые протокол + id + канал не дублируются).

| Протокол | Модуляция, мкс | Проверка |
|---|---|---|
| Nexus / FreeTec / Solight / TFA 30.3209, Rubicson / TFA 30.3197 | PPM 1000/2000, 36 бит, повтор 3 раза | CRC-8 `0x31` у Rubicson; диапазоны у Nexus |
| Prologue / ThermoPro TX2 / NC-7104 | PPM 2000/4000, 36 бит, повтор 4 раза | тип-ниббл 9/5, диапазоны |
| Acurite 609TXC | PPM 1000/2000, 40 бит | сумма байтов |
| LaCrosse TX141TH-Bv2 / TX141-Bv2/Bv3 / TFA 30.3221 | PWM 208/417, синхро 833 | LFSR digest-8 |
| Bresser 3CH / Renkforce DM-7511 | PWM 250/500, синхро 750, инверсия | сумма байтов; температура в °F |
| Acurite 592TXR / башенка | PWM 220/408, синхро 620, 7 байт | сумма + чётность |
| Fine Offset WH2 / WH2A / WH5 / TFA 30.3157 | PWM 500/1500 ±160 | CRC-8 `0x31` |

Результат декодера датчика: название протокола, id, канал, температура (допустимый диапазон примерно -40..70/80 °C), влажность (если есть), признак батареи.

**Пульты.** Если ни один датчик не подошёл, `decRemote` смотрит на кластеры длительностей импульсов. Два значимых кластера с отношением 1.6..4.5 наводят на мысль о пульте. Пульт с постоянным кодом (тип EV1527/PT2262: 24 или 25 бит, длинный импульс около 3× короткого, повтор не меньше двух раз) выдаётся как «Remote». **Сам код не сохраняется**: только 16-битный хеш 20 адресных бит как отпечаток и номер кнопки (младшие 4 бита, приведённые к 1..4). Пульт с плавающим кодом (8+ ровных импульсов преамбулы, пауза-заголовок 3..12 мс, 65..67 бит) выдаётся как «Rolling» с хешем постоянной части. По сохранённому пульт воспроизвести нельзя.

**Анализатор** (`ookAnalyze`) работает на каждой посылке: кластеризует длины импульсов и пауз (±30 % плюс 30 мкс), берёт значимые кластеры (не менее 8 % элементов), угадывает модуляцию (PWM, если период импульс+пауза постоянен не менее чем в 70 % пар, иначе Manchester; PPM, если у пауз две ширины), считает строки и биты (самая длинная строка), вычисляет отпечаток формы (хеш ширин, числа бит и строк, не зависящий от кода) и классифицирует: `sensor`, `remote`, `rolling`, `unknown`, `noise`. Для датчиков показываются сырые байты; для пультов и неизвестных сигналов сохраняется только начало рисунка импульсов (12 пар, хвостовая пауза ограничена 4 мс), по нему код восстановить нельзя.

### Таблица датчиков

`src/subghz/sensors.cpp`: до `SENS_MAX` = 16 записей с ключом (протокол, id, канал); при переполнении вытесняется самая давняя. В записи — последние температура, влажность, батарея, RSSI, счётчик и времена. Во флеш ничего не сохраняется. `sensOutside()` возвращает температуру самого сильного датчика, слышанного за последние 10 минут; её использует «Радиопогода» как температуру за окном. Порядок показа: сначала термодатчики, потом пульты, внутри группы — по силе сигнала (давно не слышанные опускаются).

### Веб-режим

Пока на планшете открыта вкладка Sub-GHz, `subWebUse()` включает CC1101 (`src/web/web.cpp`); если вкладка не опрашивала данные 4 с, чип выключается.

## IR (`src/probe/ir*`)

Вопрос, на который отвечает раздел: «чей это пульт?».

### Захват (`ir.cpp`)

ИК-приёмник на GPIO 1 уже снимает несущую 38 кГц. Периферия RMT в ESP32 записывает длительности: разрешение 1 мкс, 4 блока памяти (запасной вариант — 2), 192 символа на пачку. Импульсы короче 3 мкс отфильтровываются как помехи; тишина дольше 12 мс завершает пачку. Выход приёмника инвертирован (0 = вспышка), поэтому символы RMT преобразуются в плоскую последовательность `вспышка, пауза, вспышка, ...`, начиная со вспышки; два отрезка одного уровня подряд склеиваются; хвостовая тишина длиннее 10 мс отбрасывается. Пачки из 3 и более длительностей идут в декодер. В буфере хранится до `IR_RAW_MAX` = 128 длительностей. ИК-светодиод (GPIO 2) настроен как выход и удерживается в LOW. Приёмник работает, только пока открыт раздел или планшет подписан на `ir`.

### Декодирование (`ir_decode.cpp`)

Длительности сравниваются с номиналом с широким допуском, потому что дешёвые приёмники удлиняют вспышки примерно на 100 мкс: `0.7·T - 100 <= v <= 1.3·T + 100`. Проверки идут в таком порядке:

| Протокол | Заголовок, мкс | Данные |
|---|---|---|
| повтор NEC | 9000 + 2250, не более 4 длительностей | «кнопку держат»: повторяет последний код NEC |
| NEC / NEC-EXT | 8800 + 4400 | 32 бита, младшим вперёд, вспышка 560, пауза 1690 = 1 / 560 = 0; если за байтом адреса (и команды) следует его инверсия — это NEC с 8-битным адресом, иначе NEC-EXT с 16 битами |
| LG | 8800 + 4400 | 28 бит, старшим вперёд |
| JVC | 8800 + 4400 | 16 бит, вспышка 525, пауза 1575 / 525 |
| Samsung | 4500 + 4500 | 32 бита, 560/1690 |
| Kaseikyo (Panasonic и родня) | 3456 + 1728 | 48 бит, 432/1296; адрес = код производителя |
| Sony SIRC | 2400 + 600 | 12, 15 или 20 бит; бит несёт ширина импульса (1200 = 1, 600 = 0) |
| RC6 | 2666 + 889 | Manchester, единица 444 мкс, 16/20/24/32 бита, бит toggle; режим 6 — вариант Windows MCE |
| RC5 | единица 889 мкс | Manchester, 14 бит, toggle, 5-битный адрес, 6-битная команда (+ бит расширения RC5X) |
| всё остальное | от 7 длительностей | `RAW` с хешем квантованных длительностей (одна и та же кнопка даёт один хеш) |

Декодер «расстояния между импульсами» (`pulseDist`) требует точного числа вспышек: лишние означают, что это другой протокол.

### Марка и повторы

`irBrand()` делает только честные догадки по протоколу и адресу («вероятно»): например, NEC с адресом `0x04` — LG TV, Samsung с адресом `0x07` — Samsung TV, Kaseikyo с кодом `0x2002` — Panasonic, RC5 с адресом 0 — Philips TV. Неизвестные адреса NEC дают «пульт NEC (много марок)»; длинные RAW-кадры (70+ бит) наводят на кондиционер.

Повторы (`irFeed`): тот же протокол, адрес и команда в пределах 250 мс (RC5/RC6: 400 мс и тот же бит toggle) — это повтор, а не новое нажатие. Кадр повтора NEC повторяет последний код NEC. В истории хранится 8 нажатий; повторы обновляют время последней записи. Нажатие колеса очищает историю. На планшет уходит только последняя пачка (до 64 длительностей в JSON).

### Ограничения

Пульты кондиционеров (длинные кадры) показываются только как RAW; декодер их не опознаёт. Частота несущей не измеряется (приёмный модуль рассчитан на 38 кГц). Ничего не передаётся.

## NFC (`src/probe/nfc*`)

Вопрос, на который отвечает раздел: «что это за карта?». Только чтение. Палка ничего не пишет и ничего не эмулирует.

### Железо и опрос (`nfc.cpp`)

PN532 по I2C (адрес `0x24`, SDA 8, SCL 18), сброс на GPIO 45 (LOW — сон). `nfcStart()` сбрасывает чип, запрашивает версию прошивки (`GetFirmwareVersion`, до 3 попыток, потому что первый кадр будит чип), включает обычный режим SAM и ограничивает число попыток поиска пассивной цели двумя, чтобы опрос не зависал; если ответа нет, состояние становится «нет считывателя» (нажатие колеса повторяет попытку). `nfcStop()` выключает радиополе и переводит чип в сон.

Опрос не блокирует основной цикл: каждые 120 мс отправляется `InListPassiveTarget` (тип A; каждый третий опрос — тип F / FeliCa, 212 кбит/с), затем управление возвращается, а ответ забирается, когда чип сообщит о готовности; если за 400 мс ответа нет, запрос отменяется ACK-кадром и начинается заново. Более 8 неудачных обменов подряд означают, что считыватель пропал с шины.

Кадры соответствуют формату PN532 (преамбула, длина и её дополнение, TFI `D4`, данные, контрольная сумма); в ответах проверяются заголовок `D5`, `cmd+1` и сумма. Приёмный буфер — 64 байта; обрезанный ответ помечается.

Пока виден тот же UID, карта считается «всё ещё приложена» (убрана — после 900 мс без ответа) и повторно не читается.

### Что читается при появлении карты

Для карт ISO 14443-A (ATQA, SAK, UID до 10 байт):

1. Если в SAK есть бит ISO-DEP (`0x20`), отправляется одна команда: `SELECT 2PAY.SYS.DDF01` (PPSE). Положительный ответ означает «платёжная карта (EMV)». Ответ **не сохраняется**: приёмный буфер затирается. Ни номер карты, ни имя, ни история не читаются.
2. Если SAK = `0x00` и младший байт ATQA = `0x44` (Ultralight / NTAG), читается capability container (страница 3). Если он начинается с `0xE1` (метка размечена под NDEF), страницы с 4-й читаются блоками по 16 байт до 160 байт, пока не встретится терминатор `0xFE`, и разбирается сообщение NDEF. Затем `GET_VERSION` по байту объёма отличает NTAG213/215/216 от Ultralight EV1.
3. Иначе семейство определяется только по ATQA/SAK.

FeliCa: читается только идентификатор (IDm).

### Классификация (`nfc_model.cpp`)

По SAK: `0x08`/`0x88` — MIFARE Classic 1K, `0x18` — Classic 4K, `0x09` — Mini, `0x10`/`0x11` — Plus 2K/4K, `0x28`/`0x38` — Classic со смарт-чипом; SAK `0x00`: NTAG213 / 215 / 216 (по байту объёма GET_VERSION `0x0F`/`0x11`/`0x13`), Ultralight EV1 (`0x0B`/`0x0E`) или общий Ultralight/NTAG; ISO-DEP с ATQA `0x0344` — DESFire, иначе обычная смарт-карта; остальное — «Метка ISO 14443-A». У каждого семейства есть подсказка («проездной / ключ от двери · вероятно»): формулировки намеренно осторожные, потому что тип карты не доказывает, для чего её используют.

### NDEF и приватность

Записи NDEF: URI (с таблицей префиксов), текст, MIME только по типу (настройки Wi-Fi показываются как «настройки Wi-Fi (скрыто)», содержимое, где может быть пароль, не выводится), внешние типы. До 3 записей по 64 символа; управляющие символы заменяются пробелами; оборванные хвосты UTF-8 отрезаются. UID показывается скрытым: только первые 2 байта (`04A2••`), в том числе в JSON. Последние 4 прикладывания хранятся только в ОЗУ.

### Ограничения

Малая дальность антенны PN532; опрашиваются только типы A и F (нет типа B и ISO 15693). Секторы MIFARE Classic не читаются (ключи не используются и не подбираются). У карт со случайным UID префикс каждый раз другой.
