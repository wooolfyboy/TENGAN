# Applications: tablet page, TENGAN Tablet, TENGAN Desktop, installer

TENGAN (the device, "the stick") has a small screen and one wheel. Everything bigger is done by four
programs that live outside the firmware:

| Program | Where it runs | Source | Delivered as |
|---|---|---|---|
| **Tablet page** (HQ, city, sound, settings...) | any browser, inside the two apps below | `tools/webapp/` | gzip inside the firmware (`src/web/tablet_page.h`) |
| **TENGAN Tablet** | Android | `app/` | `tengan_tablet.apk` (release asset) |
| **TENGAN Desktop** + PC monitor | Windows, macOS, Linux | `tools/desktop/`, `tools/pc_monitor/` | `tengan_desktop.exe`, `.app` zip, AppImage |
| **Installer** | Chrome / Edge (Web Serial) | `tools/flasher/` | `flash_tengan.html`, one file |

All of them speak the same protocol with the device (HTTP `/api/*`, SSE stream on port 81, or the same
JSON over a USB cable with `@`-lines); the protocol itself is described in the protocols chapter. This chapter
is about how the programs are built and why they are built that way.

```
                 tools/webapp/src ──build.py──► tablet_page.h (gzip, in firmware flash)
                                                      │ served by the device as /, /full, /tablet
        ┌─────────────────────────────────────────────┼───────────────────────────────┐
        ▼                                             ▼                               ▼
  browser on a phone/tablet                  TENGAN Tablet (Capacitor)        TENGAN Desktop (pywebview)
  http://192.168.4.1/                        own copy + self-update           page comes over USB (@G) or
                                             from the stick (/api/pagever)    http://192.168.4.1/full (Wi-Fi)
```

## 1. The tablet page (`tools/webapp`)

### 1.1 Layout of the sources

One offline HTML file, no framework, no external requests. `tools/webapp/src/index.html` is a shell; the
build inlines everything else:

| Path | Role |
|---|---|
| `src/index.html` | header (logo, nav, status line), `#main`, `#boot` canvas, modal; `/*@INLINE path*/` markers |
| `src/hud.css` | layout and DOM-based UI (settings, chips, toggles) |
| `src/fonts.css` | generated by `make_fonts.py`: WOFF2 subsets in base64 |
| `src/core/` | `util.js` (brushes, text, post effects), `theme.js`, `i18n.js`, `canvas.js`, `gl.js`, `store.js` (data model), `stream.js` (link), `gps.js`, `boot.js`, `app.js` (tabs, frame loop, quality) |
| `src/views/` | one file per section: `overview`, `hq`, `ble`, `wifi`, `sub`, `sound`, `pc`, `probe` (IR / NFC), `astro`, `gallery`, `weather`, `settings` |
| `i18n/ru.json` | Russian dictionary (about 425 entries) |
| `mock.py` | fake stick for development without hardware (`python3 tools/webapp/mock.py page.html [port] [denko\|kurenai] [en\|ru]`) |

All code shares one global `T` (theme, helpers, views list) and `S = T.S` (latest data from the stick). A view
is an object pushed to `T.views` with `id`, `title`, `want` (which streams it needs), optional `subs`
(sub-tabs), and `mount / frame / unmount`. Nav buttons are created from `T.views`.

### 1.2 Build: `build.py` -> `tablet_page.h`

`python3 tools/webapp/build.py` does the following, in order:

1. Reads `index.html` and replaces every `/*@INLINE path*/` with the file's text after a *light minify*
   (`slim()`: drops blank lines, comment-only lines and indentation; it never touches code inside a line).
2. Replaces `/*@DATA*/` with sky data (`T.DATA`: stars, constellation lines, land outlines, names). The data is
   **parsed from the firmware header** `src/gallery/astrodata.h`, so the device and the page cannot drift apart.
3. Replaces `@@VERSION@@` with the `VERSION` file.
4. Embeds `i18n/ru.json` (always) and the start language (`/*@LANG*/'en'`).
5. Fails if any external `src=`/`href="http..."` is left: the page must work with no internet.
6. Compresses with gzip level 9 and `mtime=0` (reproducible bytes) and writes `src/web/tablet_page.h`:
   `TABLET_GZ[]` (PROGMEM), `TABLET_GZ_LEN`, `TABLET_HTML_SHA`, plus a `// html-sha256:` comment.

Current numbers: about 478 KB of HTML, 219 668 bytes gzipped. CI has a size budget of 231 000 bytes for the
gzip (`build.yml`, "Size budgets").

**Version = SHA-256 of the uncompressed HTML.** Both the firmware (`/api/pagever`, USB `@g ... begin`) and the
clients use it to answer "is my copy current". The hash is of the HTML, not of the gzip, because different zlib
versions produce slightly different gzip bytes for the same input.

`--check` (CI step "Tablet page is up to date") rebuilds the HTML in memory and compares only the hash stored in
`tablet_page.h`. If a source changed and the header was not regenerated, the build fails with "run
build.py". Other modes: `--html out.html --only-html [--lang ru]` writes just the HTML (and `pagever.txt` next
to it) for the APK, the mock server and tests, without touching the firmware.

The firmware always gets the English start build; the language is switched at run time (next section), so one
page serves both languages.

### 1.3 Languages: English source, Russian dictionary

Interface text in the code is English. `core/i18n.js` translates **at the point of output**:

- Canvas: `CanvasRenderingContext2D.fillText / strokeText / measureText` are wrapped. Layout code therefore
  measures the translated text, and no view needs to know about languages. In English the wrapper does nothing.
- DOM: strings go through `T.tr(s)` where they are inserted (tabs, settings, dialogs).
- Explicit choice: `T.L('English', 'Русский')`.

Dictionary rules (`ru()`): exact match first; otherwise known phrases inside the string are replaced (word
boundaries, longest phrase first, built into one big regular expression); letter case is kept
(`DEVICES` -> `УСТРОЙСТВА`). Results are cached in a `Map` (cleared above 4000 entries), so a frame costs a few
lookups. Phrases shorter than 3 characters are matched only as whole strings.

The language follows the device: `st.lang` from the stream (checked every 400 ms) calls `T.setLang()`, which
clears the text-fit cache, stores the choice in `localStorage` and calls the redraw hooks in `T.onLang`.
`?lang=` overrides it for tests. Texts that come from the device (settings pages, option names) arrive in the
device language already and are only reloaded on a language change.

### 1.4 Rendering: Canvas 2D, plus one shared WebGL context

- **Canvas** (`core/canvas.js`): `T.canvas(parent)` makes an opaque (`alpha:false`) 2D canvas and a
  `ResizeObserver`. Drawing is in CSS pixels; the backing store is scaled by
  `min(devicePixelRatio, 3, T.RES / longestSide) * T.RS`, where `T.RES = 1920` caps the long side and `T.RS` is the
  adaptive factor (section 1.5). A hidden section (size < 2 px) is not resized, so the picture and memory survive.
- **Text and HUD brushes** (`util.js`): `T.header`, `T.panel` (cut corners), `T.brackets`, `T.segBar`, `T.spark`...
  mirror the firmware's `ui.cpp` so the tablet looks like the stick. The unit `T.unit(W,H) = min(W/80, H/50)`
  gives 16 px on a 1280x800 tablet and scales proportionally.
- **WebGL** (`core/gl.js`): *one* context for the whole app, on an off-screen canvas. A view draws its scene with
  a fragment shader (`T.GL.prog / begin / quad`) and copies the result onto its own 2D canvas with one
  `drawImage`, then draws the HUD on top in 2D. One context avoids the browser's limit on WebGL canvases and
  re-creation when switching sections. Without WebGL (old tablet, `?nogl`, context lost) `T.GL.ok = false` and
  views draw an older 2D version.
- **Themes** (`core/theme.js`): a theme is only a palette plus fonts (`T.C`, `T.RGB`, `T.HEAT`, `T.COOL`,
  `T.ALERT`, fonts). Drawing code is the same, so a theme costs nothing per frame. Three themes:
  `denko` (cyan HUD), `kurenai` (black / white / red, flat: no glow, no scanlines), and `mono` (black and white,
  used only while starting, because the stick's theme is not known yet). WebGL shaders are written in DENKO
  colors; in KURENAI one function appended to every fragment shader (`THEMED`) maps cyan and orange to red and
  everything else to gray of the same brightness (`T.GLK = 1`). The theme comes from `st.theme` or `?theme=`.
- **Post effects** (`util.js`): bloom is computed on a 1/4 and 1/8 downscale merged into one small light map
  and applied in one pass; the backdrop gradient and the scanline / vignette layer are pre-rendered once per
  size. The rule behind it: fewer full-screen repaints per frame.
- **Fonts**: JetBrains Mono (all text), Exo 2 (DENKO headings), Oswald (KURENAI headings) and a subset of
  IPAGothic with only the glyphs of the 天眼 seal and kanji used in HQ and weather. `make_fonts.py` subsets them
  (Latin and Cyrillic from the same family, so nothing shifts on a language change) and writes base64 WOFF2
  into `fonts.css`. It needs `fonttools` and `brotli`; CI does not rebuild it.

### 1.5 Frame loop, 60 fps and adaptive quality (`core/app.js`)

One `requestAnimationFrame` loop. `FPS_CAP = 60`: on 120 / 144 Hz screens extra frames are skipped, and after
a stall the loop does not catch up in a burst (`dt` is clamped to 0.1 s). `S.tick(dt)` smooths data every
frame (values arrive in jumps, the picture flows), then the current view's `frame(dt, t)` runs. During the
start animation the view waits (`App.hold`) while data keeps arriving.

Quality adapts like a game does, once per second from the measured FPS:

| Condition (checked each second, not while the tab is hidden) | Action |
|---|---|
| FPS < 50 for 2 seconds and `T.RS > 0.6` | resolution `T.RS` -= 0.1 (canvases are refitted, the GPU stretches the image) |
| still slow and `T.RS` is at 0.6 for 3 seconds | **LITE**: `T.Q.bloom = 0`, scanlines off (the only heavy effect) |
| FPS >= 58 for 8 seconds | `T.RS` += 0.1, up to a ceiling |
| it got slow again within 15 s of raising | the ceiling is lowered to avoid oscillation |

A fresh start (`App.fresh()`) happens on every section or sub-tab change: quality returns to 100 % with a 2.5 s
grace period, so only a section that really cannot keep up is degraded. The top bar shows
`NN FPS · 80% · LITE` when "Show FPS" is on (Settings > Actions) or with `?debug`.

Do not confuse this **render LITE** (glow off) with the **LITE page** (section 1.7): the first is an automatic
quality step of the full scene, the second is a different, light page.

Sections stay alive: `App.go()` hides the previous section instead of destroying it and keeps the last
`KEEP = 3`; the oldest is unmounted. Returning shows the city with everything it has grown at once. Last
section and sub-tab are remembered in `localStorage` (`view`, `sub_<id>`).

### 1.6 Data link (`core/stream.js`) and the store

Streams, in order of preference:

1. **SSE** `http://<stick>:81/stream?want=ble,wifi,...` (a second port, so slow page loads do not block it).
   Events: `st ble wifi snd sub pc sat wx ir nfc sens`. `want` is set by the current view (`App.rewant()`), and
   the device switches radios on only for what is watched.
2. **Polling** `/api/*` if SSE does not open within 5 s: every 125 ms, one request at a time (the next one only
   after the previous answer); the stick gets `?tab=` to choose radios. After 8 s it tries SSE again.
3. **USB bridge** inside TENGAN Desktop: `window.TenganUSB` (`want / api / poll`). `fetch()` of `/api/...` is
   replaced so the page does not notice the cable.

`core/store.js` (`S`) keeps the last data and does the smoothing: `T.steady(deadband, tau)` ignores jitter
smaller than the dead band and lets big changes flow. It also implements the **alert rules** shared with the
device and the desktop app: "new" device (not seen this session, within `al_newfor` seconds, near enough),
warm-up after connect (`al_warm`), tracker alerts, and the activity meter (mean of enabled sources scaled by
sensitivity; thresholds `al_warn` / `al_alarm`). The thresholds are the device's own settings
(`/api/settings`, page `alert`, re-read every 15 s). `tools/desktop/events.py` is a Python copy of these rules.

Device labels ("my AirPods"): the stick stores them and sends them as the 8th field of each BLE row; the page
keeps a local copy for 6 s so a new name shows at once (`S.setLabel`, `/api/label`). The dialog warns when a
device rotates its address (`stable:false`).

Settings view (`views/settings.js`): a pure DOM page built from `/api/settings` (pages, items, types
`enum / range / bool / info`); a change is applied immediately and rolled back if `/api/set` fails. "Actions"
page: device screen, LEDs, FPS counter, and (app only) update check.

### 1.7 Start sequence: launch, intro, choice (`core/boot.js`)

Every page open runs three phases (skipped with `?noboot`):

1. **Launch** (black-and-white `mono` theme). Five steps with a progress bar: `LINK` (stream open),
   `DEVICE` (first `st`), `RADIO` (Bluetooth on), `DATA` (first devices), `RENDER` (scene drew 3 frames). Each
   step waits at most 6 s, so with no device the scene still opens. Once the first four steps are done the
   Bluetooth > City scene is mounted under the curtain, so it warms up during the intro.
2. **Intro** (2.7 s, as `core/boot.cpp` on the stick): crosshair, rings, sweep, "decoding" of the name, the
   天眼 seal, wipe. A tap skips it; with `prefers-reduced-motion` it is skipped. At its start the stick's theme and
   language are applied at once (the 9 s fallback in `theme.js` switches to DENKO if no device answers).
3. **Choice** (only in a browser opened at the device root `/`; not in the apps, not at `/full` or `/tablet`):
   two panels, **LITE** (light page for a phone, goes to `/lite`) and **FULL** (this scene). While you choose,
   the city under the curtain keeps growing, which is why FULL opens with a populated city.

Entry URLs served by the device (`src/web/web.cpp`): `/`, `/full`, `/tablet` give the same gzip page (with
`Cache-Control: no-cache`); `/lite` and the old `/phone` give the light page.

### 1.8 The LITE page (`/lite`)

`src/web/web_page.h` is a separate, small page (about 27 KB in the firmware, plain strings; no gzip, no
WebGL): header with battery, tabs Overview, Bluetooth, Wi-Fi, Sub-GHz, Sound, System, Update. Each tab polls
its own `/api/*` with `async` loops, next request only after the previous answer (intervals: 3 s overview,
2 s Bluetooth, 5 s Wi-Fi, 60 ms Sub-GHz and Sound, 3 s System). The Sub-GHz and Sound tabs keep the radio /
microphone on while open. The language is set by the device (`<html lang>` is written when served). The Update
tab uploads OTA firmware. LITE exists for old phones and for people who do not need the full scene; it has a
single theme.

### 1.9 URL parameters (development and tests)

| Parameter | Effect |
|---|---|
| `host=ip[:port]` | stick address (default `192.168.4.1` in the app, page host in a browser) |
| `sse=port` | SSE port (default 81; the mock server uses 8091) |
| `theme=denko\|kurenai`, `lang=en\|ru` | fix the theme / language |
| `nogl` | disable WebGL, force 2D fallbacks |
| `noboot` | skip launch, intro and choice |
| `debug` | show FPS and update status |
| `shot` | for README images: all effects on, no FPS counter, no adaptation |

## 2. TENGAN Tablet (`app/`)

An Android shell around the same page. Capacitor 7.6.10, plugin `@capacitor/geolocation` 7.1.8, `minSdk 23`,
`targetSdk 35`, application id `dev.tengan.app`. The shell exists because a browser cannot do what the app does:

- **The page loads from the app itself** (`capacitor.config.json`: `androidScheme: http`, `cleartext: true`,
  `allowMixedContent`), so it can call `http://192.168.4.1` without mixed-content or origin trouble (the stick
  also answers with `Access-Control-Allow-Origin: *`). With the tablet connected to the TENGAN Wi-Fi there is no
  internet and none is needed.
- **Screen stays on**, immersive full screen (`MainActivity.java`).
- **GPS** (`core/gps.js`, only when `T.native`): `watchPosition` with high accuracy (`timeout 30000`,
  `maximumAge 15000`). The page computes the sky and globe from these coordinates, and the stick gets them
  too (`/api/loc?lat=&lon=`) so its own sky is "from here": at the first fix, after a move of about 1 km
  (0.009 deg), or every 10 minutes; if the request fails it is retried. The firmware validates the numbers
  (|lat| <= 90, |lon| <= 180, not both zero) and calls `setGpsCity()`. The header shows `GPS ±12m`. Permissions
  in the manifest: `INTERNET`, `ACCESS_COARSE_LOCATION`, `ACCESS_FINE_LOCATION` (GPS is not required).
- **No choice screen**: in the app the LITE / FULL choice is skipped.

### 2.1 Build

CI job `android` (`build.yml`), also locally:

```
cd app && npm ci && npm run sync     # sync = build.py --html www/index.html --only-html  +  cap sync android
cd android && ./gradlew assembleRelease
```

`www/` is generated (git-ignored); `pagever.txt` lands next to `index.html` and is packed into the APK assets.
`versionCode` comes from the CI run number (`APP_VERSION_CODE`), `versionName` from the `VERSION` file.
`app/make_icons.py` redraws the launcher icons and splash (the 天眼 seal) with Pillow and IPAGothic; run it only
when the artwork changes.

### 2.2 APK signing through secrets

Updates install over an old version only if the signature is the same, so releases are signed with one TENGAN
key that is **not in the repository**:

| Secret | Content |
|---|---|
| `TENGAN_KEYSTORE_B64` | the PKCS12 keystore, base64 |
| `TENGAN_KEYSTORE_PASSWORD` | its password (the key password is the same) |

The CI step decodes the keystore to `$RUNNER_TEMP/tengan.p12` and exports its path as `TENGAN_KEYSTORE`.
`app/android/app/build.gradle` signs with alias `tengan` when `TENGAN_KEYSTORE`, the password and the file all
exist; otherwise it uses Android's debug key. Rules: a **release** (tag `v*` or manual `release_tag`) with no
keystore secret fails the job; a normal push or a fork only warns, and gets a throwaway-signed APK that works
but will not update over the official one (Android sees a different app).

### 2.3 Self-update of the page from the stick

The firmware always contains the newest page, so the app does not need a new APK for page changes. A new APK
is needed only when the native shell changes. `MainActivity.java` does this:

```
every 30 s, 3 s after start, 1.5 s after resume:
  GET http://192.168.4.1/api/pagever          (2.5 s timeout)   -> {"sha": "...", "gz": N}
  sha == current?  -> done
  GET http://192.168.4.1/full                 (15 s timeout), gunzip if the body starts with 1f 8b
  sha256(html) == sha ?  no -> keep the old page ("bad hash")
  write filesDir/stickpage/index.html + pagever.txt (temp file + rename)
  store the path as Capacitor's serverBasePath, bridge.setServerBasePath(path) -> page reloads
```

The "current" version is the `pagever.txt` of the downloaded copy, or the one bundled in the APK assets. The
hash check means a half-downloaded or corrupted page is never activated. After an APK update
(`lastUpdateTime` changed) the downloaded copy is forgotten, because the new APK may carry a page newer than the
stick's. The status (`start`, `check`, `same xxxxxx`, `download`, `updated`, `bad hash`, `no stick: ...`) is
exposed to the page by the `TenganUpdate` plugin (`status()`, `check()`); with `?debug` it appears in the header
as `UPD ...`, and Settings > Actions has a "check now" button.

## 3. TENGAN Desktop (`tools/desktop`, `tools/pc_monitor`)

One program: the HQ window (the same page) + the PC monitor + tray, popups and widget. Python, window by
**pywebview** (Windows: WebView2 / WinForms, macOS: WebKit, Linux: Qt WebEngine through PySide6, forced with
`PYWEBVIEW_GUI=qt`). User data lives in `%APPDATA%\TENGAN`, `~/Library/Application Support/TENGAN` or
`~/.config/TENGAN`: `desktop.json` (settings, key `alerts` holds popup / widget / window preferences),
`desktop.log`, `webview/` (browser storage).

### 3.1 Files

| File | Role |
|---|---|
| `tengan_desktop.py` | `Link` (USB), `Monitor`, local HTTP server, launcher, `App`, window setup |
| `events.py` | alert "brain" without windows or libraries: `Engine.feed / pop / snapshot` |
| `overlay.py` | popups, widget, tray (`pystray`), `SseFeed`, single instance, Win32 helpers |
| `overlay_html.py` | HTML of popups and widget (DENKO / KURENAI, EN / RU) |
| `test_events.py` | tests of the brain; run in CI on macOS and Linux |
| `fake_stick.py`, `render_preview.py`, `smoke_run.py` | development and CI helpers |
| `build_exe.py`, `build_xplat.py` | PyInstaller builds |
| `../pc_monitor/pc_monitor.py` | the monitor: metrics, media keys, "now playing", PC audio, orbits |

### 3.2 Connection modes and the launcher

At start a small launcher page (served from `http://127.0.0.1:47321/`, the port moves up to +19 if busy)
offers **USB**, **Wi-Fi** and **AUTO** (USB if the device is on the cable, else Wi-Fi). The last choice is
remembered and auto-starts after a countdown. F11 is full screen, F2 returns to the launcher, F3 toggles the
widget.

- **USB**: everything over one serial port (CDC, 115200, DTR / RTS off so the device is not reset). The port is
  found by Espressif VID `0x303A`, then by description (`jtag`, `esp32`), then by name (`/dev/ttyACM*`,
  `/dev/cu.usbmodem*`). Internet on the computer stays on. Lines starting with `@` are the app protocol:
  `@W want=...` (subscribe, repeated every 2 s as "I am here"), `@Q id /api/...` (request) -> `@R id json`,
  `@E event json` (stream events, same JSON as SSE), `@G id` -> `@g id begin size sha`, `@g id offset base64`,
  `@g id end` (the page, gzip in 1.5 KB base64 chunks), `@X web` (the Web section is closed on the device).
  Lines without `@` are the PC monitor wire (`PC ...`, `PV`, `KEY`, `AUD`).
- The page is fetched over the cable, un-gzipped, checked against the SHA (up to 3 tries: an occasional lost
  64-byte USB packet gives "arrived incomplete" or a broken gzip) and served to the window as `/full` with a
  small injected script (the USB bridge, F-keys, widget tab on the right edge). `Link.poll()` long-polls events
  for the page every 0.25 s.
- **Wi-Fi**: the computer joins the device's access point and the window opens `http://192.168.4.1/full`.
  If a cable is also plugged in, the PC monitor still works over it.

Language of the window: the device's last known language (`st.lang`, stored in `desktop.json`), otherwise the OS
language (Windows UI language, macOS `AppleLanguages`, `LANG`).

### 3.3 PC monitor (`pc_monitor.py`)

Runs inside Desktop (class `Monitor`) or standalone (`start_pc_monitor.bat`, which installs `psutil`,
`pyserial` and optional libraries). Once per second it sends one line: `PC cpu= freq= c=<per-core> ram= ramu=
ramt= dsk= dr= dw= nd= nu= up= top= host= ts= tz= [bat= plug=]`; then volume (`PV vol= mute=`), the
"now playing" line and the **process city** (`PP`: up to 24 programs: top CPU users first, then biggest by
memory, plus the active window; computed in a background thread because walking hundreds of processes takes
1-2 s on Windows). Every minute it sends satellite orbits (`TLE`: ISS, Tiangong, Hubble from celestrak.org,
refreshed every 6 h, cached in `tle_cache.txt`); `ts` / `tz` give the device an exact time for the sky.

The device sends back `KEY VOLUP|VOLDN|MUTE|PLAY|NEXT|PREV` (the Media page) and `AUD ON` / `AUD OFF` (the
Sound section asks for the computer's audio).

| Feature | Windows | macOS | Linux |
|---|---|---|---|
| Media keys | virtual keys (`keybd_event`) | AppleScript: Spotify, then Music; system volume | `playerctl` (MPRIS), volume by `pactl` or `amixer` |
| Volume read | `pycaw` | AppleScript | `pactl` / `amixer` |
| Track title | system media panel (`winrt`), else window title | Spotify / Music | any MPRIS player |
| PC audio for Sound | WASAPI loopback (`PyAudioWPatch`) | not available (no loopback without a driver) | PulseAudio / PipeWire monitor (`sounddevice`) |
| Foreground app in city | yes | no | no |

PC audio: 32 spectrum bands (60 Hz - 8 kHz, geometric, same edges as the device microphone), level, 64-point
wave and XY, about 30 frames per second as `PA ...` lines, with auto-gain; it listens only while the device
keeps asking (4 s timeout).

On Linux the serial port needs the `dialout` group; if opening fails with a permission error the launcher shows
the `usermod -aG dialout` hint.

### 3.4 Alerts: events, popups, widget, tray

**`events.py` (the brain).** `Engine.feed(ev, data)` takes the same events as the page (`ble ir nfc sens wx st
snd`) and applies the same rules as `store.js`; `pop()` returns ready notices; `snapshot()` feeds the widget.
Thresholds (`al_*`) come from the device (`/api/settings`, re-read every 30 s) so they are the same on the
stick, tablet and computer; the app's own preferences are `kinds`, quiet hours, per-minute limit and so on.
Anti-spam design:

- warm-up after every (re)connect; a device that returns is not new;
- a tracker nearby is reported once per 10 minutes per device;
- same-kind notices within `merge_s` (2 s) merge into one ("4 NEW DEVICES");
- limit `per_min` (6) per minute, alarms may go up to twice the limit; quiet hours (a nearby tracker can pass);
- IR: a held button is one press; NFC: the same card within 5 s is one; 433 MHz: first snapshot is only a
  baseline; temperature: change of at least 1 degree and at most once per 10 minutes; battery: crossing 15 %
  down while not on USB; link lost / restored only if the state holds 5 s.

**Data path.** USB: `Link._push` -> `App.on_stick_event` -> `Engine.feed_raw`. The subscription is the
page's own plus `ble,ir,nfc,sens,wx` (`Link.set_extra`), so alerts work with HQ on another tab or the window
hidden (a hidden browser throttles the page). Wi-Fi: `SseFeed` opens its own stream to `:81`. The device has
two SSE slots for Wi-Fi clients plus one USB slot, so in Wi-Fi mode the window page and the alert stream use both
slots; a tablet joining at the same time would push one of them out. For alerts, USB mode is recommended. A 5 Hz
`ticker` pops notices, updates the widget and every 5 s reads the device theme to pick the style.

**Popups** (`overlay.Popups`): one frameless, always-on-top window with a stack of up to 3 cards; it resizes to
the stack and hides when empty; a click opens HQ; corner and duration are settings. Style follows the device
theme (DENKO: black with orange caution stripes, red blinking alarm; KURENAI: black with a white frame and a
slanted seal plate), or fixed. Option "system notifications" uses the OS instead (macOS AppleScript, Linux
`notify-send`, Windows `pystray` notify).

**Widget** (`overlay.Widget`): a mini radar, the activity bar (平穏 / 活発 / 注意 / 警報) with per-source marks,
outdoor temperature, last remote and card, battery and link. Position and size are saved, opacity and
click-through are settings. The widget lives on its own: closing the main window with the widget on, or with
the tray on, hides the window instead of quitting; quit comes from the tray or the widget's right-click menu.

**Tray**: `pystray` menu: open HQ, widget, popups, system notifications, click-through, style, corner, mode
(USB / Wi-Fi / Auto), alert settings, quit. A second launch of the program does not open a second copy: it
shows the first window (Windows: named mutex; macOS / Linux: probe of port 47321; then `GET /__app/show`).

**Autostart**: Windows `HKCU\...\Run`, macOS a LaunchAgent plist, Linux `~/.config/autostart/*.desktop`, with
the `--tray` key (go straight to tray).

### 3.5 Platform specifics

- **Windows**: WebView2 never rendered in a window created hidden, so popups and the widget are created visible
  and **parked off-screen** (`-32000, -32000`); "show" is a move. Opacity and click-through use Win32
  `WS_EX_LAYERED` / `WS_EX_TRANSPARENT`; `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE` keeps them out of the taskbar,
  Alt-Tab and focus. Widget dragging uses the system move (`WM_NCLBUTTONDOWN` on the form's UI thread, after
  releasing the WebView2 mouse capture), which is smooth. Work area for corners comes from `SPI_GETWORKAREA`
  divided by the DPI scale. The EXE is not code-signed, so SmartScreen may warn on first start.
- **macOS**: widget dragging with pywebview `easy_drag`; the tray runs detached inside the Cocoa loop; not
  signed by Apple, so first open is right-click > Open; no PC audio loopback.
- **Linux**: Qt WebEngine; widget drag via `.pywebview-drag-region` (`easy_drag` on Qt installs an app-wide event
  filter and crashed); system notifications by `notify-send`; the tray needs AppIndicator or X11.
- Status of checks (`tools/desktop/WIDGET.md`): popups, widget, drag verified on Windows (200 % scaling); tray,
  system notifications, `focus=False` and transparency in WebView2 were still unverified; macOS and Linux
  builds are smoke-tested in CI but not with real hardware.

## 4. The installer (`tools/flasher`)

`flash_tengan.html` is **one file** that holds the firmware and the flashing library, so the user opens it in
Chrome or Edge, presses **Install firmware**, picks the device and waits about a minute. No addresses, no
files. It uses Web Serial and **esptool-js 0.5.4** (Apache License 2.0, `esptool-js.LICENSE`; the license text is embedded in the page).

### 4.1 How it is made (`make_flasher.py`)

CI step "Make image and installer" first merges the full image with `esptool.py merge_bin`:

```
0x0 bootloader.bin   0x8000 partitions.bin   0xe000 boot_app0.bin   0x10000 firmware.bin   ->  tengan_full_0x0.bin
```

then `python tools/flasher/make_flasher.py dist/tengan_full_0x0.bin dist/flash_tengan.html <tag>`:

- takes `flasher_template.html` and fills placeholders: fonts (the same JetBrains Mono and Exo 2 as the tablet,
  taken from `fonts.css`), both languages' texts, the esptool-js bundle, and the firmware as **base64**;
- esptool-js is an ES module that ends with `export{...}`; the script replaces that line with
  `window.__esptool={...}` so the page's own module can use it;
- checks the image first (byte 0 is `0xE9`, partition table magic `AA 50` at `0x8000`), refuses otherwise;
- stamps version and build date; fails on an unfilled `{{` placeholder.

Size is about 3.9 MB; CI budget 4 150 000 bytes. The page is English / Russian by browser language
(`localStorage` `lang`, switch at the top).

### 4.2 What gets written, and why settings survive

The flasher does **not** write the whole image. The image layout is: bootloader (0x0), partition table
(0x8000), **NVS (0x9000-0xE000, device settings)**, otadata (0xE000), application (0x10000). It writes two
parts only:

| Part | Address | Contents |
|---|---|---|
| 1 | `0x0` ... `0x9000` | bootloader and partition table |
| 2 | `0xE000` ... end | otadata (`boot_app0`) and the application |

The NVS range between them is skipped. A flash chip erased there would reset the user's settings (language,
theme, labels, alerts), so a normal update keeps them. Other details: `eraseAll: false`, `compress: true`,
`flashSize / flashMode / flashFreq: 'keep'`, baud 921600 (ROM talk at 115200). Writing `otadata` (`boot_app0`) together with the application at `0x10000` makes the bootloader
start that application.

Flow in the page: port filter `usbVendorId 0x303A` (Espressif) -> `ESPLoader.main()` -> must report
**ESP32-S3**, otherwise "this is not a TENGAN board" -> `writeFlash` with a progress bar -> `loader.after()`
(hard reset) -> "Done, unplug the cable and plug it back in". Errors: port busy (close TENGAN Desktop and other
serial tools: only one program can own the port) or a message with the technical log below.

Wireless updates and rollback are a different path (OTA through the Web section; the new firmware is tried
first and the old one restored if it does not run for 15 s); the installer is for first install, for
recovery, and for people who prefer a cable.
