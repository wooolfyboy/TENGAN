# Protocols and wire formats

TENGAN talks to the outside world over three channels: its own Wi-Fi access point (HTTP + SSE), a USB cable (text lines on the CDC serial port) and, for firmware updates, an HTTP upload. This section describes each of them as they are implemented in the code. The sources are `src/web/web.cpp`, `src/link/serout.cpp`, `src/pc/pc.cpp`, `tools/pc_monitor/pc_monitor.py`, `tools/desktop/tengan_desktop.py` and `tools/webapp/src/core/stream.js`.

```
                 Wi-Fi AP "TENGAN-XXXX"                       USB (CDC serial)
 phone / tablet ───────────────┐                  ┌──────────────── PC app (tools/desktop)
   :80  HTTP  /  /lite /full /api/*  /update      │                  or PC monitor (tools/pc_monitor)
   :81  SSE   /stream?want=…                      │   "@W/@Q/@G" ->   "@E/@R/@g/@X" <-
   :53  DNS   * -> 192.168.4.1                    │   "PC/PV/PM/PP/PA/TLE" ->   "KEY/AUD" <-
                               ┌──────────────────┴──┐
                               │  TENGAN (web.cpp,   │
                               │  pc.cpp, serout.cpp)│
                               └─────────────────────┘
```

The same JSON handlers (`apiHandle()`) and the same event generators (`sseTick()`) serve both Wi-Fi and USB clients, so a page does not need to know which transport it runs on.

## 1. Wi-Fi access point and captive portal

All of this exists only while the **Web** section is open on the device (`webStart()` / `webStop()` in `src/web/web.cpp`). Closing the section switches Wi-Fi, the extra Bluetooth scanning and the Sub-GHz / microphone / IR / NFC helpers off.

| Parameter | Value |
|---|---|
| Mode | `WIFI_AP_STA` (the STA half is used for network scanning) |
| SSID | `TENGAN-` + last two bytes of the MAC in hex, e.g. `TENGAN-A1B2` |
| Password | 8 digits: FNV-1a (32 bit) over the 6 MAC bytes, modulo 10^8, zero-padded; stable for a given device |
| Channel / hidden / max clients | 6 / no / 4 (`WiFi.softAP(ssid, pass, 6, 0, 4)`) |
| IP | `192.168.4.1` (Arduino default for softAP) |
| QR code on the screen | `WIFI:T:WPA;S:<ssid>;P:<pass>;;`, generated with `esp_qrcode` (max 45x45 modules) |

**Captive portal.** A `DNSServer` on port 53 answers every name with `192.168.4.1`. The HTTP server's `onNotFound` handler replies `302` with `Location: http://192.168.4.1/`. Phones probe connectivity with well-known URLs, get a redirect and offer to open the page by themselves.

**Radio sharing.** The AP and Bluetooth share one radio, so while Web is open Bluetooth runs at a lower duty cycle (`bleLowDuty(true)`, scan window 45 instead of 99) and is switched on only when somebody looks at BLE data. Wi-Fi network scanning (for the Wi-Fi tab) does not scan all channels at once: that pulls the radio off the AP channel and clients drop. Instead, every 1.5 s (`SCAN_STEP_MS`) one channel is listened to for 90 ms; channels 1..13 in turn, a full round takes about 20 s. Results are kept per BSSID (up to 64, `NET_MAX`) and forgotten after 60 s of silence.

## 2. HTTP server (port 80)

### Pages

| Route | What it returns |
|---|---|
| `/` | The tablet app (the launcher: splash, LITE / FULL choice). One gzip file, `Content-Encoding: gzip`, `Cache-Control: no-cache` |
| `/full`, `/tablet` | The same gzip file. `/full` is what the Android app and the desktop app download; `/tablet` is the old address |
| `/lite`, `/phone` | The light phone page (`src/web/web_page.h`): tabs Overview, Bluetooth, Wi-Fi, Sub-GHz, Sound, System, Update. The page language follows the device (`<html lang>` is written while serving) |
| any other path | `302` to `http://192.168.4.1/` |

The gzip comes from `src/web/tablet_page.h`, generated by `tools/webapp/build.py` from `tools/webapp/src/`. The header also holds `TABLET_HTML_SHA` (SHA-256 of the **uncompressed** HTML, the page version) and `TABLET_GZ_LEN`. The build uses `mtime=0` so identical sources give identical bytes.

### API (`/api/*`)

All API routes are `GET`, return `application/json` with `Cache-Control: no-store` and `Access-Control-Allow-Origin: *` (the tablet app runs on its own origin). `?tab=` is an optional hint (see below). The list of routes is the `API_PATHS` array in `src/web/web.cpp`; every route goes through `apiHandle()`.

| Route | Parameters | Purpose and response |
|---|---|---|
| `/api/ble` | | Bluetooth overview: `on`, `count`, `macs`, `dev[]` (`id`, `r` RSSI, `t` type, `v` vendor, `n` name, `age`, `m` address count), `sens` (used by `/lite`; see `bleJson` in `src/ble/ble_core.cpp`) |
| `/api/bledev` | `id` | Details of one device from the list (`bleDevJson`) |
| `/api/wifi` | | `{"scanned":bool,"nets":[{"s":ssid,"b":bssid,"v":vendor (OUI),"r":rssi,"c":channel,"e":"open/WEP/WPA/WPA2/WPA3/WPA2-ENT"}]}` |
| `/api/sub` | `m` mode (0 spectrum, 1 monitor, 2 sensors), `b` band (0..3, default 1) | Switches the CC1101 into that mode and returns the current state (`subJson`: spectrum `cur`/`peak` arrays, or monitor `floor`, `burst`, `events`, `rssi[]`, `ev[]`) |
| `/api/sens` | `b` band | 433 MHz sensors (mode 2): `on`, `pk`, `noise`, `sensors[]`, `last` |
| `/api/snd` | | Microphone / sound: `en`, `ok`, `lv`, `pk`, `hz`, `e`, `b[]` (bands 0..100) |
| `/api/pagever` | | `{"sha":"<sha256 of the page>","gz":<gzip size>}` - the page version, see section 6 |
| `/api/settings` | | All settings by page: `{"pages":[{"id","name","items":[{"k","name","hint","type":"enum/range/bool/info","v",…}]}]}` |
| `/api/set` | `k`, `v` | Change one setting. `enum`: option name or number; `bool`: `1/true/on`; `range`: integer. Reply `{"ok":true,"item":{…}}` or `{"ok":false,"err":"…"}`. Theme, language, battery and version are read-only here ("change it on the device") |
| `/api/label` | `id`, `n` | Give a Bluetooth device a name (empty `n` clears it). Reply `{"ok":true,"stable":bool}`; `stable:false` means the device rotates its address, so the label will be lost when it changes |
| `/api/act` | `a`, `v` | Actions: `a=screen&v=0/1` turn the device screen off/on (work continues); `a=leds&v=0` LEDs off |
| `/api/pckey` | `k` | Media key for the laptop: `VOLUP VOLDN PLAY MUTE NEXT PREV`. `{"ok":true}` only if the PC program is alive (see section 4) |
| `/api/loc` | `lat`, `lon` | The tablet sends its GPS; the device computes sky and globe from it. Rejected if out of range or exactly 0,0 |
| `/api/info` | | Uptime, battery (`soc`, `mv`, `ma`, `t`, `tte`, `ttf`, `rem`, `full`, `usb`, `chg`), chip temperature, free heap/PSRAM (KB), `cli` (Wi-Fi clients), `nets`, `build`, `theme`, `ver`, `lang`, `rst` / `rstStep` (last reset reason and step, from `src/core/crumb.cpp`), `ssid` |
| `/api/ver` | | `{"build":…,"slot":"<running OTA partition label>","max":<free space for a new image>}` |
| `POST /update` | multipart, file field | Firmware upload, see section 5 |

While the Web section is closed (this only happens over USB), the radio-related routes (`ble`, `bledev`, `wifi`, `sub`, `sens`, `snd`) answer `{"ok":false,"err":"open Web on the stick"}`; settings, info, labels, actions, `pckey`, `loc`, `pagever` and `ver` still work.

**The `?tab=` hint.** The `/lite` page and the polling fallback of the tablet add `tab=ov|ble|wifi|sub|snd|sys|upd` to every request. `noteTab()` stores it, and `webTick()` uses it to decide what to run: Bluetooth for the Overview and Bluetooth tabs, network scanning for Overview and Wi-Fi, and so on. Nothing else runs ("only what is looked at"). Once an SSE client is connected, its subscription (`want=`) takes over from the tab hint.

**Polling intervals of `/lite`** (`web_page.h`): Overview 3 s, Bluetooth 2 s, Wi-Fi 5 s, Sub-GHz and Sound 60 ms, System 3 s, plus `/api/info` every 8 s on every tab. The CC1101 and the microphone shut themselves down if nobody polled them for 4 s.

## 3. SSE stream (port 81)

The second "door" is a separate raw TCP server (`NetworkServer`) on port 81, so that a long-lived stream does not block the HTTP server. It accepts only `GET /stream…`, anything else gets `404`.

```
GET /stream?want=ble,wifi,snd&sm=0&sb=1 HTTP/1.1

HTTP/1.1 200 OK
Content-Type: text/event-stream
Access-Control-Allow-Origin: *
retry: 1500

event: st
data: {"name":"TENGAN","up":123,...}
```

### Subscription: `want=`

The request line is scanned by `parseWant()` for substrings: `ble`, `wifi`, `snd`, `sub`, `pc`, `wx`, `ir`, `nfc`, `sens` in `want=` (comma-separated, default `ble,wifi`), plus `sm=` (Sub-GHz mode, default 0) and `sb=` (band, default 1). `ir` and `nfc` start from the current generation counter, so old taps are not replayed. The `st` event is always sent.

Capacity: 2 Wi-Fi clients (`SSE_NET`) plus 1 slot for the USB app (`USB_SLOT`), 3 in total. If both Wi-Fi slots are busy a new connection evicts slot 0. The side effects of a subscription are real: `wx` turns on Bluetooth, microphone and a 433.92 MHz monitor; `sens` switches the CC1101 into packet-decoding mode; `ir` and `nfc` start those receivers and stop them 4 s after the last subscriber is gone.

### Events

| Event | When | Content (JSON) |
|---|---|---|
| `st` | every 2 s (first one on connect) | `name`, `up` s, `bat` % (-1 if unknown), `mv`, `usb`, `chg`, `cli`, `heap` KB, `theme` (`denko`/`kurenai`), `ver`, `lang`, `rst`, `rstStep`, `radio` (letters of active radios: `b` BLE, `w` Wi-Fi scan, `s` Sub-GHz, `m` mic, `p` PC link, `i` IR, `n` NFC), `lp` = `[loop avg ms, loop max ms, frame avg ms, frame max ms, fps, % of lines sent]` |
| `sat` | once per connection, right after the first `st` | `{"city","lat","lon","sats":[[name, epoch, n0, ndot2, inc, raan0, ecc, argp0, m0, a],…]}`: orbit elements; the tablet computes the sky and globe itself (Kepler + J2) |
| `ble` | 1 s, if subscribed | `{"on","n","m","d":[[id, rssi, "type", "vendor", "name", age_s, addresses, "label"],…]}`: up to 80 devices sorted by RSSI; arrays instead of objects to save bytes |
| `wifi` | after each new scan result, not periodically | same as `/api/wifi` |
| `snd` | every 40 ms (up to 25/s) | `{"en","ok","lv","pk","hz","e","b":"<32 bytes hex>","w":"<64 int8 samples hex>"}` |
| `sub` | every 140 ms (about 7/s), if the CC1101 is running | same as `/api/sub` |
| `pc` | 1 s | laptop load, see below |
| `wx` | 1 s | "radio weather": `ok`, `cond`, `clouds`, `wind`, `rain`, `storm`, `thunder`, `trend`, `ble`, `turn`, `sub`, `subPk`, `snd`, `pk`, `hist[]`, `temp`, `hum`, `tsrc` |
| `sens` | on a new 433 MHz packet (at most every 150 ms) or every 1 s | same as `/api/sens` |
| `ir` | on each received IR burst | `{"p":protocol,"addr","cmd","bits","brand","rep","raw":[µs…],"t"}` |
| `nfc` | on each card tap | `{"fam","hint","uid" (masked),"atqa","sak","ndef":[…],"present","t"}`; without a reader `{"err":"no reader"}` |

The `pc` event is `{"live":0|1, …}`; while the PC program is silent it is just `{"live":0}`. Otherwise it carries `age`, `host`, `cpu`, `ghz`, `c[]` (per core), `ram`, `ru`, `rt` (GB), `disk`, `dr`/`dw` (MB/s), `nd`/`nu` (KB/s), `bat`, `plug`, `up`, `top`, `vol`, `mute`, optionally `trk` (`t`, `a`, `app`, `play`, `pos`, `dur`; `pos` is extrapolated by the device between updates) and `city` (towers `[name, cpu%, MB, active, slot]`).

### Delivery rules

- Writes never block. The socket is used with `MSG_DONTWAIT`; what does not fit stays in a per-client buffer (`pend`) and is flushed on the next pass.
- High-rate events (`snd`, `sub`) are "droppable": if the client still has unsent data, the frame is skipped. A client whose buffer exceeds 24000 bytes is disconnected.
- Nagle is turned off (`setNoDelay`), otherwise small frames wait for a delayed ACK.
- The device tracks total bytes sent and shows speed and active streams (`BLE`, `WIFI`, `SUB`, `SND`, `PC`, `WX`, `IR`, `NFC`, `USB`) on its screen.

### Client side (`tools/webapp/src/core/stream.js`)

The page opens `EventSource("http://<host>:81/stream?want=…")` and registers one handler per event name; the same handler table `H` is used for USB. If the stream does not open within 5 s the page falls back to **polling** `/api/*` every 125 ms with a staggered schedule (sound every pass, BLE every 8th, `/api/info` every 16th, Wi-Fi every 40th, Sub-GHz every 2nd) and retries the real stream after 8 s. The status badge reads LIVE (SSE), POLL, USB, `USB · OPEN WEB ON TENGAN` or NO LINK. Host and port can be overridden with `?host=` and `?sse=` (used with `tools/webapp/mock.py`, which emulates the device).

## 4. USB channel between the stick and a computer

The stick enumerates as a USB CDC serial port (`ARDUINO_USB_CDC_ON_BOOT=1`). Baud rate is irrelevant for native USB; the computer-side code opens at 115200 with DTR and RTS off (otherwise the stick may reset on connect). The computer finds the port by Espressif VID `0x303A`, then by description (`jtag`/`esp32`), then by name (`/dev/ttyACM*`, `/dev/cu.usbmodem*`).

The wire is **text lines** ending in `\n`. Two programs may sit on the other end, and they speak the same protocol family:

- `tools/pc_monitor/pc_monitor.py` - a console program (laptop monitor), started with `start_pc_monitor.bat`;
- `tools/desktop/tengan_desktop.py` - the desktop app (window with the FULL page + the same monitor inside + tray, popups, widget). Only one of them can own the port.

The device parses incoming lines in `src/pc/pc.cpp` (`pcPoll()` reads at most 2048 bytes per loop pass; the line buffer is 1024 bytes, a longer line is dropped as garbage). Lines starting with `@` go to `webLinkLine()` in `web.cpp` (the app protocol); the rest belong to the monitor protocol.

### 4.1 Monitor protocol (laptop <-> stick)

Computer to device:

| Line | Rate | Meaning |
|---|---|---|
| `PC cpu=23.4 freq=3.10 c=12,40,5,… ram=61.2 ramu=9.8 ramt=16.0 dsk=71 dr=0.0 dw=0.1 nd=12 nu=3 up=86400 top=chrome host=LAPTOP ts=<unix> tz=<sec> [bat=87 plug=1]` | 1 s | Load figures as `key=value` separated by spaces: CPU %, GHz, per-core % (up to 16), RAM % / used GB / total GB, disk usage %, disk MB/s read/write, network KB/s down/up, uptime s, top process, host name (spaces removed), battery. `ts` > 1700000000 sets the device clock (`astroSetTime`) for sky and satellites |
| `PV vol=35 mute=0` | with `PC`, and at once after a key press | Laptop volume |
| `PM<TAB>playing<TAB>pos<TAB>dur<TAB>app<TAB>title<TAB>artist` | 1 s | Now playing; TAB-separated because titles contain spaces. Empty `PM` = nothing is playing. `pos`/`dur` in seconds, -1 unknown |
| `PP<TAB>name,cpu*10,MB,active<TAB>…` | 1 s | "Process city": one entry per program (all its processes together); up to 24 towers |
| `TLE<TAB>name<TAB>line1<TAB>line2` | every 60 s per satellite | Orbit elements (ISS, Tiangong, Hubble). The PC program fetches them from CelesTrak every 6 h and caches in `tle_cache.txt` |
| `PA <level*10> <hz> <32 bands hex> <64 wave hex> <64 L,R pairs hex> <stereo 0/1>` | about 30/s while requested | Laptop audio analysis: bands, waveform and XY (stereo) |

Device to computer:

| Line | Meaning |
|---|---|
| `KEY VOLUP` / `VOLDN` / `PLAY` / `MUTE` / `NEXT` / `PREV` | Remote control: the PC program presses the media key. Sent when the PC page "Media" is open (wheel = volume, press = play/pause) or from the tablet via `/api/pckey`. Not sent if the PC data are stale |
| `AUD ON` | In the Sound section, with source "auto" or "PC" the stick asks for audio; repeated every 1.5 s, and only while the PC data are live (`pcSendLine()` is silent otherwise). The PC side stops 4 s after the last request |
| `AUD OFF` | Stop sending `PA` |

The PC data count as "live" while the last `PC` line is younger than 10 s (`pcLive()`; the comment in `pc.h` says 3 s, the code uses 10). The city is live for 6 s. On the PC side the Windows build uses WASAPI loopback (PyAudioWPatch), Linux uses the PulseAudio/PipeWire monitor through `sounddevice`; on macOS speaker audio is not available and the stick shows its own microphone. Keys: Windows virtual keys, macOS AppleScript, Linux `playerctl` / `pactl` / `amixer`.

### 4.2 App protocol (`@` lines)

This is "the page over USB" for the desktop app. No Wi-Fi is needed; the computer keeps its Internet.

PC to device:

| Line | Meaning |
|---|---|
| `@W want=ble,wifi&sm=0&sb=1` | Subscribe (the same string as in the SSE URL). The app repeats it every 2 s as "I am here". |
| `@Q <id> /api/...?a=1&b=%D0%9F` | Request. The path and query go through the same `apiHandle()` as HTTP; `%XX` and `+` are decoded |
| `@G <id>` | Send me the page |

Device to PC:

| Line | Meaning |
|---|---|
| `@E <event> <json>` | A stream event: same names and JSON as SSE (`st`, `ble`, `snd`, …) |
| `@R <id> <json>` | Reply to `@Q` with the same `id` |
| `@g <id> begin <gz bytes> <sha256>` | Start of the page transfer |
| `@g <id> <offset> <base64>` | A chunk: 1536 raw bytes (up to 2048 base64 characters), sent only while the output queue is shorter than 8 KB so the stream is not delayed |
| `@g <id> end` | End of the page |
| `@X web` | "The Web section is closed, open it" (at most once per 1.5 s) |

Behaviour:

- The USB client occupies the third SSE slot. `@W` creates or replaces its subscription; the same event generator then writes `@E` lines instead of SSE frames. If there is no `@W` or `@Q` for 6 s the slot is freed (app closed, cable pulled) and the radios go back to sleep.
- A `@W` after more than 8 s of silence counts as a new connection and **opens the Web section** on the stick (`navOpen(&webSection)`). If the user closed Web by hand while the app stays connected, the stick does not reopen it by itself and only answers `@X web`.
- The radios of the stick (BLE, CC1101, microphone) are therefore driven by the app exactly as by a tablet, with the same policy.
- The page is sent as gzip. The app checks the size, unpacks it, compares the SHA-256 (prefix of the hex string) and retries up to 3 times: USB CDC occasionally loses a 64-byte packet, which shows up as "page arrived incomplete" or a bad gzip.
- **Output queue** (`src/link/serout.cpp`). Everything the device writes over USB (`@E`, `@R`, `@g`, `KEY`, `AUD`) goes through one 64 KB ring buffer in PSRAM so that lines never interleave. Lines are stored whole (`serOutBegin` / `Part` / `End`). Writes never block: `serOutPump()` writes as much as `Serial.availableForWrite()` allows, up to 8 times per loop pass. Droppable lines (audio and spectrum frames) are refused if more than 12 KB is queued; any line that does not fit in the remaining space is refused.

### 4.3 How the desktop app presents it

`tools/desktop/tengan_desktop.py` runs a local HTTP server on `127.0.0.1:47321` (a fixed port, so that the page's `localStorage` survives) and a `Link` object that owns the serial port (a "keeper" thread reconnects on cable loss). In **USB mode** the window opens `http://127.0.0.1:47321/full`: the page was fetched with `@G` and the app injects a small bridge `window.TENGAN_DESKTOP={mode:'usb'}` plus `window.TenganUSB`:

| Local route | Maps to |
|---|---|
| `/__link/want?q=…` | `@W` (merged with extra subscriptions `ble,ir,nfc,sens,wx` when popups or the widget are enabled) |
| `/__link/api?p=/api/…` | `@Q`, waits for `@R` (3 s timeout; `{"ok":false,"err":"timeout"}`) |
| `/__link/poll` | long poll (up to 0.25 s): returns `[["st",{…}],["ble",{…}],…]`; `["_x","web"]` / `["_x","nostick"]` are service messages |

`stream.js` then replaces `window.fetch` for `/api/` URLs, so the page code is unchanged. In **Wi-Fi mode** the window simply loads `http://192.168.4.1/full`; if the cable is also connected, only the monitor part uses it. Other local routes (`/__app/*`) are the app's own (launcher, preferences, tray, test popup) and are not part of the stick protocol. Popups and the mini-widget are described in `05-applications.md`, section 3.4.

## 5. Firmware update over the air (OTA) and rollback

Web section -> `/lite` page -> **Update** tab. The file is sent with `POST /update` (`multipart/form-data`, field name `fw` in the page; the upload handler is `otaUpload()`).

Accepted files (names from the release workflow `.github/workflows/build.yml`):

- `tengan_firmware_ota.bin` - the plain application image (`firmware.bin`);
- `tengan_full_0x0.bin` - the merged image for USB flashing at address 0x0.

How the handler tells them apart: it buffers the first `0x8002` bytes. If the bytes at `0x8000` are `AA 50` (the partition table magic), the file is a merged image, and everything up to `0x10000` (bootloader, partition table) is skipped; the application is written from there. Otherwise the buffered head is written as is. The first byte of the written data must be `0xE9` (ESP image magic), otherwise "not an ESP32 firmware file". Files below 32 KB are rejected ("file is too small").

Steps:

1. `UPLOAD_FILE_START`: the Bluetooth radio is switched off so that all airtime goes to the upload; the device screen shows a progress bar (`drawWebOta`).
2. `UPLOAD_FILE_WRITE`: `Update.begin(UPDATE_SIZE_UNKNOWN)` and `Update.write()` write into the **other** OTA slot (the board uses the `default_16MB.csv` partition table with two app slots). `crumbFeed()` is called per chunk because flash writes are slow and the main-loop watchdog (15 s) must not fire. The progress percentage is estimated assuming about 2.1 MB.
3. `UPLOAD_FILE_END`: `Update.end(true)` validates the image and switches the boot slot. On any error `Update.abort()` is called and the old firmware stays active.
4. The `POST` reply is `{"ok":true|false,"err":"…"}`. On success the device waits 600 ms and restarts; the page tells the user to reconnect to the stick's Wi-Fi in about 20 s.

**Rollback.** `src/main.cpp` defines `verifyRollbackLater()` (returns true), so a freshly written slot stays "pending verify" until the application confirms it. In `loop()` `confirmFirmware()` calls `esp_ota_mark_app_valid_cancel_rollback()` only after **15 s of uptime**. If the new firmware crashes, hangs or reboots before that, the bootloader boots the previous slot on the next reset. After a USB flash the call does nothing. `/api/ver` shows the running slot label and the maximum image size.

## 6. Self-update of the tablet page

The tablet app is a single HTML page that is **stored inside the firmware**, so the stick always carries the newest UI. Android app (`app/android/.../MainActivity.java`, Capacitor shell) updates its copy from the stick:

1. Every 30 s (and 1.5 s after the app comes to the foreground) it calls `GET http://192.168.4.1/api/pagever` (2.5 s timeout) and gets `{"sha":…}`.
2. It compares `sha` with the version of the page it currently shows: either `pagever.txt` of a previously downloaded page, or `public/pagever.txt` bundled in the APK (written by `tools/webapp/build.py`).
3. If they differ, it downloads `GET /full` (15 s timeout), computes SHA-256 of the received bytes and accepts the page only if it equals the announced `sha`. (The device sends gzip; the app unpacks it by the `1F 8B` signature, so the hash is of the plain HTML.)
4. It saves `index.html` and `pagever.txt` into the app's private storage (`stickpage`), points Capacitor's `serverBasePath` at it, and reloads the WebView. No Internet is needed, only the stick's Wi-Fi.
5. After an APK update the downloaded page is forgotten, because the APK may be newer than the stick.

The page shows the state in its header through the `TenganUpdate` plugin (`status` / `check`): `same`, `download`, `updated`, `bad hash`, `no stick`. A new APK is required only when the native shell itself changes. The desktop app in USB mode gets the same page differently: via `@G` (section 4.2), with the same SHA-256 check.

## 7. Persistent storage (NVS)

Settings are stored with the Arduino `Preferences` API (flash NVS). Namespaces found in the code:

| Namespace | Keys | Notes |
|---|---|---|
| `radar` | `range`, `thresh`, `ledbr`, `scrbr`, `dim`, `snd`, `mic`, `click`, `th2` (theme), `langv` + `lang`, `auled`, `ausrc`, `city`, `gpsok` / `gpslat` / `gpslon`, `tz`, `bltick`, `wftick`, `wrange`, `band`, alert thresholds `alnear`, `alnew`, `altrk`, `alnewf`, `alwarm`, `alsens`, `alwarn`, `alalarm`, `alcble`, `alcrf`, `alcsnd`, `alcprb`, `alblink`, `alplate` | All ints except `gpsok` (bool) and `gpslat/lon` (float). Values are clamped to their ranges on load (`src/core/settings.cpp`). Changes mark the settings dirty and are written 3 s after the last change (autosave) |
| `labels` | `l` | Blob: array of `{uint8 mac[6]; char name[21]}`, up to 32 entries; when full the oldest is evicted. Names are cut to 20 bytes at a UTF-8 boundary |
| `sats` | `n0..n3`, `a0..a3`, `b0..b3` | Satellite name and the two TLE lines, up to `SAT_MAX` = 4; written only when the epoch of a received `TLE` line changed |

`langv` is written only after a real language choice (picker or Settings); while it is absent the language picker is shown at start. The old `lang` key is only a hint for updates from early test builds. `/api/set` runs the same setter as the on-device menu (`setVal`) and so the same validation and autosave; the call is also logged in the crash "breadcrumb" (`crumb("api set k=v")`).
